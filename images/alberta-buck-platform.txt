Bootstrapping the BUCK monetary system requires three deliverables that
share one foundation:

1. *High-resolution simulation*: 10^3 - 10^4 agents (citizens earning,
   living and saving; investors; businesses; governments) transacting
   against the real BUCK contracts and AMM pools over multi-year
   horizons.
2. *Live-interactive demonstrations*: browser-hosted simulations – in
   web sites and slide decks – where an audience member creates agents,
   mints BUCK_CREDIT, executes identity-signed transfers, and watches
   background agents rebalance real AMM pools under simulated time and
   price feeds.
3. *Production platforms*: JS, native, and Python libraries with which
   the initial identity registries, insurers, and credit unions
   integrate their back-office systems – signing Identities, generating
   BuckCredit NFTs, producing BUCK account products – and on which the
   first BUCK native wallets are built (Identity "fountain" management,
   Ethereum transaction construction and signing).

The shared foundation is (a) a backend-agnostic `ChainSession' API with
expectation checking and journaling, spanning anvil, public testnets,
Tenderly overlays, and in-process JS EVMs (Tevm); and (b) a Rust
mathematical kernel – monetary arithmetic and the Identity/proving
cryptography – compiled to WASM for JavaScript and bound natively for
Python, so every platform predicts bit-identical fees, demurrage,
depreciation, and proofs.

1 Decisions of record
═════════════════════

  Settled 2026-07-02/03; revisit deliberately, not accidentally.

  • *Population target*: 10^3 - 10^4 agents.  Some "fat" (one agent
    driving many identities), but BUCK_CREDIT-bearing agents must stand
    alone.  This scale does NOT require abandoning anvil: `ChainSession'
    over anvil is the primary sim backend; `pyrevm' (in-process revm)
    remains an *optional* accelerator gated by identical-vector tests
    against anvil.
  • *No pure-Rust simulator*.  Python (and later JS) orchestrate; Rust
    holds only the deterministic math kernels.  Understandability of the
    sim and its agents is paramount: the chain API stays tidy, agents
    stay simple.
  • *JS live-interactive demos are a requirement*, not a nice-to-have.
    Record/replay does not cut it: demos must let someone set up
    simulated agents, create BuckCredit, watch balances adjust, and
    execute transfers using real identities while background agents
    rebalance the real AMM pools on simulated time and prices.  This
    implies a JS agent-simulation platform that is a *peer* of
    `alberta_buck/sim' – justified because (a) most researchers will
    never run Python, (b) most integrating organizations prefer JS, and
    (c) the demo wallet should be the *real* JS wallet signing real
    transactions.
  • *The full Identity and proving stack must be available to both JS
    and Python* for sim and application R&D.
  • *Layout*: the existing Python `alberta_buck/' keeps working
    throughout.  New Rust, JS, and Python implementations land under
    `core/', and `alberta_buck/' transitions onto them incrementally.
    Dependency rule: `core' never imports `alberta_buck'; `alberta_buck'
    may import `buck_core'.
  • *Tests*: every ported/new core capability is covered in Rust, Python
    and JS – minimal in Rust (the kernel is small and vector-driven),
    primarily in Python and JS (the platforms and bindings).
  • *The Solidity contracts are the mathematical specification.* Golden
    vectors generated by forge from the deployed-code paths are the
    cross-language ground truth; Rust/Python/JS suites assert
    byte-equality against the same vector files.

2.1 Layer 1: `ChainSession' – one testing API over every backend
────────────────────────────────────────────────────────────────

  The API is the product; execution engines plug in underneath.  It is
  the formalization of what `alberta_buck/sim/chain.py''s `Chain'
  already was, plus two ideas from the bootstrap requirements:

  • *Expectations*: every state-changing operation declares whether it
    is expected to succeed or revert (`expect=OK' default,
    `expect=REVERT').  An unexpected revert raises (as today); an
    unexpected success logs a warning and is recorded.  Expectation
    mismatches are first-class results, visible in the journal and
    countable by tests.
  • *Journal*: an append-only JSONL record of every operation – tag, op,
    function, sender, expectation, outcome, gas, tx hash, block, error.
    Journals make runs auditable, diffable across backends and
    languages, replayable for demos, and memoizable ("the test
    infrastructure remembers our results").  Journaling is off by
    default (zero hot-path cost) and enabled per-session or via
    `BUCK_JOURNAL=path'.

  Journal entry schema (one JSON object per line; unknown fields
  ignored):

  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   field      type  meaning                                             
  ──────────────────────────────────────────────────────────────────────
   `i'        int   1-based sequence number within the session          
   `tag'      str   caller-supplied label ("deploy:Buck", "saver3:buy") 
   `op'       str   `send' / `deploy' (calls are not journaled)         
   `fn'       str   contract function name or "constructor"             
   `sender'   str   from-address                                        
   `expect'   str   `ok' / `revert'                                     
   `outcome'  str   `ok' / `revert'                                     
   `matched'  bool  outcome == expectation                              
   `gas'      int   gasUsed from the receipt                            
   `tx'       str   transaction hash (hex)                              
   `block'    int   block number                                        
   `err'      str   revert reason when outcome is `revert'              
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Backends, fidelity-vs-speed:

  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   backend                runs in         role                                 
  ─────────────────────────────────────────────────────────────────────────────
   anvil (foundry)        local process   PRIMARY sim backend; fidelity anchor 
   public testnets        remote          staging, partner integration         
   Tenderly virtual nets  remote          shared demos, partner staging        
   Tevm (JS, ethereumjs)  browser / node  live-interactive demos, JS sim       
   pyrevm (optional)      in-process      acceleration, iff vectors identical  
  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━


2.2 Layer 2: the deterministic kernel – one Rust workspace, two bindings
────────────────────────────────────────────────────────────────────────

  Following the proven `holo-mutualcredit' shape (core crate ->
  `mutualcredit-js' wasm-bindgen package -> Holochain zomes), modernized
  and extended with a Python binding:

  • `buck-math': integer-only monetary arithmetic – BUCK_CREDIT
    declining-balance depreciation (discrete whole-year compounding,
    linear partial year, 100-year cap), demurrage / buckSeconds carrying
    apportionment, `fundingFactor()', PID controller arithmetic
    (rescaled ppm), fees.  No floats anywhere; U256/ppm/bp semantics
    matching Solidity.  `no_std'-compatible core, preserving the
    Holochain zome option.
  • `buck-identity': BN254 (arkworks `ark-bn254', replacing pure-Python
    `py_ecc'), Poseidon, Pointcheval-Sanders credentials, ElGamal,
    Schnorr, Chaum-Pedersen, the NIZK envelope/receipt/unilateral A1/A2
    transcripts.  This is simultaneously the wallet's production
    cryptography and the sim's scaling bottleneck (identity registration
    is why `identity-cache.json' exists).
  • `buck-wallet': Identity "fountain" management, transaction
    construction and signing (alloy), account products.  Later backed by
    a Holochain DHT – the same crates compile into zomes.
  • `bindings/js': wasm-bindgen + wasm-pack -> npm package (browser +
    Node).
  • `bindings/py': PyO3 + maturin -> wheels.

  Bit-identical discipline: forge writes golden vectors
  (`test/vectors/math-*.json') exercising the Solidity paths; Rust
  `cargo test', Python `pytest', and JS `node --test' all assert
  byte-equality against the same files.  The existing Python
  `alberta_buck/wallet' remains the executable reference during the
  port, then becomes a thin shim over the PyO3 binding.


2.3 Layer 3: agent platforms – Python today, JS as a peer
─────────────────────────────────────────────────────────

  *Python* (`alberta_buck/sim') keeps its role: the research harness –
  TOML experiments, interventions, sweeps, eqmetrics, plots.  It gains
  speed and rigor from Layers 1-2 but is not rewritten.

  *JS* (`core/js') grows into a peer platform in stages:

  1. A `ChainSession' over viem with two transports: Tevm (in-process,
     browser-capable) and HTTP (anvil / testnets) – so JS agents can
     join the SAME anvil instance as a running Python sim
     (mixed-language sims), or run standalone in the browser.
  2. A small, understandable agent API (mirroring the Python `setup()' /
     `act(day, tick)' shape) with simulated-time progression and
     price-feed plumbing, sharing the scenario TOML vocabulary.
  3. The interactive demo layer: create agents from the page, mint
     BuckCredit, transfer with REAL identities (the wasm `buck-identity'
     kernel proving in-browser), while whale/arb agents rebalance the
     AMM pools in the background.

  Divergence between the two platforms is controlled by (a) both
  consuming the same compiled kernels for all money/identity math, (b)
  the shared journal format making cross-platform runs diffable, and (c)
  a canonical scenario whose Python-run and JS-run journals are compared
  in CI (Phase 4+).

═══════════════════════════════════════════

  ┌────
  │ core/
  │   README.md            layout, build/test commands, dependency rules
  │   python/              buck_core package (pyproject; sessions, later PyO3 re-exports)
  │     buck_core/         session.py (Expect/Journal/Web3Session), artifacts.py
  │     tests/             pytest suite (primary)
  │   js/                  @alberta-buck/core (ESM; journal now, session+agents next)
  │     src/  test/        node --test suite (primary; zero deps until tevm lands)
  │   rust/                cargo workspace: buck-math (+ buck-identity, buck-wallet,
  │                        bindings/js, bindings/py as they land); minimal tests
  │   vectors/             cross-language fixtures (journal-sample.jsonl, ...)
  │ test/vectors/          forge-generated golden math/identity vectors (the spec)
  │ alberta_buck/          UNCHANGED consumer; transitions module-by-module
  └────

  Transition mechanics:

  • Bootstrap import shim: `alberta_buck/__init__.py' prepends
    `core/python' to `sys.path' when running from a checkout, until
    `buck-core' ships as an installable wheel (Phase 2).
    `alberta_buck/sim/chain.py' keeps exporting `Chain' /
    `load_artifact' / `repo_root' forever; they become re-exports.
  • Each phase flips specific `alberta_buck' internals onto `core' and
    states the regression gate that proves nothing moved (usually:
    routing smoke + canonical equilibrium vector unchanged).
  • Nothing in `core' may import `alberta_buck'.

4.4.1 Design of record (banked 2026-07-03)
╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌

  *Kernel scope* (`core/rust/buck-identity'): the deterministic crypto
  core – BN254 G1/G2 arithmetic and pairing checks (EVM `ecPairing'
  semantics: `pairing_check([(G1,G2),...]) -> bool'), keccak Fiat-Shamir
  transcripts (`keccak_scalar=/=identity_scalar'), circomlib Poseidon
  (constants build-generated from a vendored byte-identical
  `poseidon_constants.json'), and every sigma protocol the wallet
  implements: PS sign/verify/rerandomize, ElGamal, registration NIZK,
  Chaum-Pedersen approve, issuer Schnorr batch binding, verifiable
  decryption, A2 issuer re-encryption binding, deposit coupling, B1
  depositor binding, note commitments / nullifiers / id-hashes /
  `identity_leaf'.  NOT kernel: canonical-JSON identity serialization,
  the AB-RCPT/1 envelope, receipt build/verify orchestration, rendering,
  the Merkle tree container (Python/JS keep those; the tree's Poseidon
  calls hit the kernel), and Groth16 SNARK proving (stays
  snarkjs/rapidsnark).

  *Determinism rule*: kernel functions take EVERY nonce/blind as an
  explicit argument – no rng inside the kernel.  Randomness stays
  language-side, so the pinned Python `random.Random' streams
  (`vectors.py', seeded sims, paper sessions) are preserved
  draw-for-draw and the emitted artifacts stay byte-identical.

  *Delegation architecture*: each `alberta_buck/wallet' module keeps its
  exact public API and dataclasses; provers draw their nonces in Python
  (in today's order, BEFORE branching), then either call the kernel
  (default when the binding is importable) or fall through to the
  retained py_ecc reference (forced via `BUCK_IDENTITY_BACKEND=py').
  `bn254.add/mul/neg' gain a G1 fast path (py_ecc FQ tuple in, FQ tuple
  out); `pairing' stays py_ecc at the bn254 level (protocol verifiers
  use kernel pairing checks wholesale).  `poseidon.poseidon()' delegates
  the same way.

  *Dependency decision*: unlike zero-dep `buck-math', `buck-identity'
  takes `ark-bn254=/=ark-ec=/=ark-ff' 0.5 (hand-rolling a correct
  optimal-ate pairing is not a good risk) plus `tiny-keccak'; std (not
  `no_std') – arkworks is wasm-clean, and the `no_std' flip stays
  mechanical (`default-features = false') if a Holochain zome ever needs
  it.

  *Binding surface*: PyO3 module `buck_core.buck_identity' (plain-cargo
  build like `buck_math'; `num-bigint' feature so Python ints cross the
  boundary; points as `(x, y)' int tuples, G2 as coefficient-pair
  tuples, proofs as flat tuples the Python shims wrap back into
  dataclasses).  wasm package `core/js/wasm/buck_identity' with 0x-hex
  strings at the ABI and a `core/js/src/identity.js' wrapper exposing
  the BigInt-native API (plus the canonical-JSON identity serializer for
  in-browser registration).

  *Vector gates* (in addition to the acceptance list above):
  1. Regenerating `test/vectors/identity.json' (`emit-vectors'), the
     golden receipt texts, and `identity-cache.json' under the kernel
     backend produces ZERO git diff; the full forge suite stays green.
  2. A new nonce-inclusive cross-language fixture,
     `core/vectors/identity-kernel-vectors.json', emitted by the py_ecc
     REFERENCE path (`BUCK_IDENTITY_BACKEND=py'), replayed
     bit-identically by the cargo, pytest, and node suites (every prove
     call with recorded nonces, verify + negative cases,
     poseidon/keccak/curve-op rows).

  *Papers plan*: `alberta-buck-notes-flow.org',
  `alberta-buck-paper.org', `alberta-buck-receipt.org' call the wallet
  API, so kernel delegation flips their executed sessions automatically;
  each gains a visible production-kernel assertion in its transcript.
  `alberta-buck-identity-example.org' additionally gets an executable
  render target (today it renders committed RESULTS via the generic
  `doc-%') and its raw `py_ecc' curve-pedagogy cells move to the
  binding's curve ops.  `alberta-buck-proofs.org' (hand-rolled sigma
  pedagogy on raw `py_ecc', no wallet imports) is explicitly out of
  scope.

5 Risks and open questions
══════════════════════════

  • *Tevm fidelity/performance*: ethereumjs-EVM is slower than revm and
    its anvil-compat surface is partial.  Mitigation: demos are small
    populations; the identical-journal gate (Phase 4) catches semantic
    drift; anvil remains the fidelity anchor.
  • *Two agent platforms drifting*: mitigated by shared kernels, shared
    scenario vocabulary, shared journal diffing – and by keeping agents
    deliberately simple (a decision of record).
  • *Crypto port correctness*: mitigated by the executable Python
    reference, frozen fixtures, and porting transcript-by-transcript
    with vectors at every step.  The Poseidon constants and rng-stream
    pinning (`vectors.py') must be treated as immovable.
  • *wasm-bindgen/PyO3 version churn*: pin toolchains in the flake; the
    `holo-mutualcredit' wasm-bindgen pin is a cautionary tale.
  • *Open*: npm package naming/scope; whether `core/js' adopts
    TypeScript from Phase 1 (leaning yes, once tevm/viem land as
    dependencies); wheel distribution channel for partners; when to
    split `core/' into its own repository (not before partners need it).
