* Overview

The note<->eEnc re-encryption tie (=INoteBindingVerifier=) closes two gaps
the flavor-agnostic spend proof leaves open:

1. *addressed-binding* — only the recipient Identity M_rec can spend an
   A1/A2 note (without it, any registered account holding the opening can
   redeem with a self-addressed eEnc).
2. *A2 collusion* — an un-nameable note is un-spendable (without it, a
   colluding pair can substitute a different, nameable eEnc).

Commit =1e410a6= plumbed the interface and a =StubNoteBindingVerifier= into
the A1/A2 spend paths.  The real ZK circuit and verifier are being
implemented under the branch =feature/decryptability=.

** Circuit Design (=circuits/note_binding.circom=)
   :PROPERTIES:
   :STATUS: DONE
   :END:

The initial design used =EllipticCurvePippengerMult= for variable-base
scalar multiplication (=m_rec * R0=), producing ~6.3M non-linear constraints
and a 1.8 GB R1CS file — too large for practical use.

Redesigned to exploit the ElGamal structure of =eIssCommitted=:
- =R0 = r*G= and =C0 = M_I + r*M_rec= where =M_I= is the decrypted issuer
  identity.
- Instead of computing =m_rec*R0= (variable-base), the prover witnesses =M_I=
  and =r=, and the circuit verifies the ElGamal structure using only
  fixed-base scalar multiplications (=r*G= and =(r·m_rec)*G=).

Result: ~2.4M non-linear constraints, 716 MB R1CS, 25 public inputs, 58
private inputs.  The circuit compiles successfully with circom 2.2.3.

Circuit constraints:
| Constraint | Description                              | EC ops                   |
|------------+------------------------------------------+--------------------------|
| (1)        | nullifier = Poseidon3(rho, idHash, 4242) | —                        |
| (2)        | idHash = Poseidon8(eNote, eIss0)         | —                        |
| (3a)       | eEnc.R = R0 + s*G                        | s*G (fixed-base)         |
| (3b)       | eEnc.C = C0 + (s·m_rec)*G                | (s·m_rec)*G (fixed-base) |
| (4a)       | R0 = r*G                                 | r*G (fixed-base)         |
| (4b)       | C0 = M_I + (r·m_rec)*G                   | (r·m_rec)*G (fixed-base) |
| (4c)       | P_I = M_I + b*H                          | b*H (fixed-base)         |

Scalar products =sm = s·m_rec= and =rm = r·m_rec= are witnessed in 4-limb
form; the circuit constrains them against the native-field products.

** BN254 G-Generator Powers Table
   :PROPERTIES:
   :STATUS: DONE
   :END:

The =circom-lib= optimized scalar multiplication
(=EllipticCurveScalarGeneratorMultiplicationOptimised=) has precomputed
stride-8 power tables for secp256k1, brainpoolP256r1, and P256, but *not*
for BN254.  Without a matching table, the template silently produces
garbage (all-zero powers → points at infinity).

Generated =circuits/ec/powers/bn254_g_pows.circom= (8214 lines, 2.7 MB)
containing the full 32×256×2×4 precomputed powers table for G=(1,2) on
BN254, and created =circuits/ec/bn254_g_scalarmul.circom=
(=ScalarMulG()=) mirroring the existing =ScalarMulH()= template.

Makefile target: =snark-g-pows= regenerates the powers file from the
Python wallet's EC primitives.

** Witness Generation — ROOT CAUSE FOUND AND FIXED
   :PROPERTIES:
   :STATUS: DONE
   :END:

The "Assertion failed: (Fr_isTrue(&expaux[0]))" abort on the
trivially-true =dummy * dummy === 0= constraint was NOT a circuit bug,
a circom-lib BN254 incompatibility, or a powers-table error.  It was
*strict-aliasing undefined behaviour* in circom's generic (=--no_asm=)
=fr.cpp= field-arithmetic runtime, miscompiled by gcc at =-O3=.

*** Diagnosis trail

1. The G-powers table and =ScalarMulG()= were validated independently:
   the small =test_sg.circom= harness compiled to WASM produces
   =s*G= matching the Python wallet's EC implementation exactly, for
   both =s = 1= and a random 254-bit scalar.  The circuit logic is
   correct; only the C++ witness path failed.
2. Instrumenting the failing assert showed =Fr_eq(0, 0)= returning
   *false* for the operand-type combination (LONG-normal 0,
   SHORT-MONTGOMERY 0) — i.e. comparing the result of
   =Fr_mul(dummy, dummy)= against the constant 0.
3. The same =fr.o= object linked into a minimal standalone test
   returned the *correct* result for byte-identical inputs — and
   adding a =printf= inside the failing helper "fixed" it: a classic
   optimizer/UB heisenbug.
4. Mechanism: the generic =fr.cpp= passes =uint64_t*= limb arrays into
   GMP's *inline* =mpn_cmp= / =mpn_add_n= / =mpn_sub_n=, whose
   parameter type is =mp_limb_t*= (= =unsigned long*= on macOS).
   =unsigned long= and =unsigned long long= are distinct types for C++
   aliasing purposes even though both are 64-bit, and =-fpermissive=
   lets the conversion compile.  gcc =-O3= then assumes the =uint64_t=
   stores (e.g. filling the =Fr_toLongNormal= temporary inside
   =req_l1ns2= / =req_s1l2n=) cannot alias the =unsigned long= loads in
   the inlined comparison, and reads *stale stack garbage* instead.
   Whether the garbage happens to be zero depends on what the caller
   left on the stack — which is why small tests passed and the real
   circuit failed, and why the failure appeared at the earliest
   constraint involving a mixed-representation compare.

*** Fix

Two build requirements, both now encoded in
=scripts/snark/setup_note_binding.sh=:

1. Compile the generated C++ with =-fno-strict-aliasing= (in addition
   to =-fpermissive=).  This makes gcc honour the cross-type limb
   accesses and restores correct field arithmetic.
2. Run the witness generator with =ulimit -s 65520= (64 MB stack).
   The generated template-run functions allocate the expanded
   G-powers table in ~5.4 MB stack frames (=FrElement lvar[67614]=
   plus =lvarcall[67598]= per =ScalarMulG=); nested template runs
   exceed the macOS 8 MB default main-thread stack.

With both applied, the =test_sg= C++ witness generator produces a
witness whose =ScalarMulG= output matches the Python EC reference
(=CPP-WITNESS-MATCH=), on the same input that previously aborted.
The full =note_binding= circuit then generates its 196 MB witness in
~9 seconds (5.9M wires; the C++ generator itself compiles in ~9
minutes at -O3), and =snarkjs wtns check= confirms the witness
satisfies all ~5.9M R1CS constraints (=WITNESS IS CORRECT=, 27 s).

The WASM path remains unusable at full-circuit size ("memory access
out of bounds", ~5.9M wires) and is no longer needed: the pipeline is
C++-witness + rapidsnark-prove.

** Groth16 Trusted Setup — COMPLETE; two more toolchain discoveries
   :PROPERTIES:
   :STATUS: DONE
   :END:

The full pipeline now runs end to end (=make nix-snark-note-binding=) and the
real verifier is exported and on-chain verified.  Getting there surfaced two
more toolchain findings, both now encoded in the scripts:

*** Discovery 1 — snarkjs sizes the Groth16 domain on TOTAL constraints

The circuit's ~2.4M /non-linear/ constraints exceeded pot20, so a *pot22*
dev ptau (4.19M domain) was generated (=snarkjs ptn/ptc/pt2= with dev
entropy; ~4.8 GB final file, several hours of =pt2=).  The first setup then
failed anyway: at circom's default =--O1= the R1CS carries the 2.4M
non-linear constraints PLUS ~3.5M /linear/ ones, and =snarkjs groth16 setup=
sizes the domain on the *total* (6,137,856 -> needs pot23).

Fix: compile with =--O2= (full linear-constraint simplification).  Result:
*2,407,838 constraints, 0 linear*, R1CS 748 MB -> 471 MB, witness 196 MB ->
73 MB (2.4M wires), and the =--O2= pass costs only ~90 s of compile time.
pot22 fits with 1.8M constraints of headroom.  (Caught by a new fail-fast
guard in the setup script -- =snarkjs= exits 0 even on "circuit too big".)

*** Discovery 2 — snarkjs 0.7.5 exports the VK already EIP-197-ordered

With the verifier exported and the proof verifying off-chain (snarkjs AND
rapidsnark), the on-chain test still rejected it -- =ecpairing= returned
=PrecompileError= (malformed G2 point).  Root cause: =fix_verifier_g2.py=
was written for an older snarkjs whose Solidity template embedded the VK G2
constants (beta/gamma/delta) in =[x_re, x_im, y_re, y_im]= order; *snarkjs
0.7.5 already emits them EIP-197-ordered*, so swapping them corrupts the
verifier.  Only the /proof-B/ swap is still wanted (the repo stores/packs
=pi_b= in proof.json natural order -- the caller-side swap that
=snarkjs generatecall= would otherwise do).

Fix: =fix_verifier_g2.py --b-only= (new flag; default behaviour unchanged
for the older committed verifiers), used by =setup_note_binding.sh=.
*Latent caveat for the other circuits:* re-running e.g. the g1tie setup
under snarkjs 0.7.5 with the default full fix would corrupt /its/ verifier
the same way -- =make snark-test-regression= exists to catch exactly this.
