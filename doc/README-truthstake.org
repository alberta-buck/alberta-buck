* Design Philosophy

  The Alberta Buck needs reliable commodity prices (Gold, Silver, energy, agricultural
  products) to compute the BUCK_K multiplier that maintains purchasing-power parity.
  Chainlink provides this today, but depends on a trusted node-operator set.  TruthStake
  is a decentralized alternative: a prediction-market oracle where *anyone* can report
  values, and the mechanism's economics guarantee that honesty is the dominant strategy.

  The core insight: *truthful people should be able to depend on the truth being
  eventually revealed, and harvest the investment of the liars when it is.*

** The Three Mechanisms

   TruthStake combines three independent mechanisms that reinforce each other:

   1. *Kalman filter* -- extracts the true signal from noisy, potentially adversarial
      observations.  Each reporter's influence is determined by their historical accuracy,
      not by vote count or stake size alone.

   2. *Stake redistribution* -- reporters post collateral on their submissions.  After
      settlement, accurate reporters collect the stakes of inaccurate ones.  The entire
      reward pool is redistributed weighted by accuracy and submission order.

   3. *Challenge escalation* -- when a participant suspects manipulation, they can pay to
      demand a larger quorum, a longer settlement window, and amplified stakes.  This
      makes sustained manipulation exponentially expensive while requiring only a single
      honest challenger to trigger the defense.

** Why Early Reporters Earn More

   The first accurate reporter takes the most risk: they submit before seeing others'
   values, with no crowd to validate against.  The mechanism rewards this courage via an
   exponential early-submission bonus.  Among equally accurate reporters, the first
   submitter earns significantly more than the last.

   This creates a race to report truthfully and early, rather than waiting to see what
   others submit.  It also prevents "free-riding" where reporters copy earlier submissions
   without doing independent observation.

* Kalman Filter Oracle

  The oracle maintains a scalar Kalman filter for each tracked value.  The filter has two
  state variables:

  - =x= :: the current best estimate (normalized to ~1.0 relative to a reference price)
  - =P= :: the uncertainty of the estimate (variance)

  On each submission, the filter computes a Kalman gain K that determines how much to
  trust the new observation vs. the existing estimate:

  #+begin_example
  K = P / (P + R)           # R is the reporter's measurement noise
  x = x + K * (z - x)      # z is the submitted value (normalized)
  P = (1 - K) * P           # uncertainty decreases
  #+end_example

  Between rounds, uncertainty grows by the process noise Q:

  #+begin_example
  P = P + Q                 # price may have drifted since last round
  #+end_example

** Reporter Measurement Noise (R)

   Each reporter's R is derived from their track record -- an exponential moving average
   of their squared relative error across all past settlements:

   #+begin_example
   After each settlement:
       rel_error = |submission - settled_value| / settled_value
       ema_sq_error = alpha * rel_error^2 + (1 - alpha) * ema_sq_error
       R = max(0.0001, ema_sq_error)    # proven reporters
       R = 1.0                          # new reporters (< 3 settlements)
   #+end_example

   New reporters start with R=1.0 (high noise, low influence).  As they prove accurate,
   R drops toward 0.0001.  An adversary who submits biased values accumulates high R and
   is effectively muted by the filter.

** Normalization

   The Kalman filter operates on values normalized by a reference scale (the initial
   estimate).  This makes all parameters (P, Q, R, gating thresholds) scale-independent:
   the same configuration works for Gold at $2900 and Silver at $32.

** Gating

   Submissions beyond a configurable number of standard deviations from the current
   estimate are silently rejected (stake returned, no penalty).  This prevents extreme
   outliers from destabilizing the filter during its early, high-uncertainty phase.

* Stake Redistribution

** Round Lifecycle

   1. *Open* -- a new round begins; Kalman uncertainty grows by Q (time propagation)
   2. *Submit* -- reporters post (value, stake) pairs; each submission updates the Kalman
      filter and is assigned a sequential index (0 = first)
   3. *Challenge* (optional) -- a challenger posts a bond to escalate
   4. *Settle* -- the Kalman estimate becomes the settled value; stakes are redistributed

** Payout Computation

   At settlement, submissions are classified as "honest" (within tolerance of the settled
   value) or "dishonest" (outside tolerance).

   Each honest reporter's share is:

   #+begin_example
   early_bonus = 2^(-index / halflife)                # 1.0 for first, decays exponentially
   accuracy_bonus = 1 - (rel_error / tolerance)        # 1.0 for perfect, 0.0 at threshold
   share = (1 + early_bonus) * accuracy_bonus
   #+end_example

   The entire reward pool (all stakes from all reporters, honest and dishonest) is
   redistributed proportionally to these shares.  Dishonest reporters receive nothing.

   Consequences:
   - Among all-honest reporters, early submitters earn slightly more than late ones
   - With adversaries present, honest reporters split the adversaries' lost stakes
   - The more adversaries, the larger the profit for honest reporters

** Example: 5 Honest Reporters (halflife=2.0)

   | Index | Early bonus | Share (1+bonus) | Payout fraction |
   |-------+-------------+-----------------+-----------------|
   |     0 |        1.00 |            2.00 |           25.3% |
   |     1 |        0.71 |            1.71 |           21.7% |
   |     2 |        0.50 |            1.50 |           19.0% |
   |     3 |        0.35 |            1.35 |           17.1% |
   |     4 |        0.25 |            1.25 |           15.8% |

   With 5 stakes of 1.0 each (pool=5.0), the first submitter receives 1.27 (profit of
   0.27) while the last receives 0.79 (cost of 0.21 for lateness).

* Challenge Escalation

  When a participant believes the current estimate is being manipulated, they post a
  challenge bond.  The challenge:

  - *Doubles the Kalman uncertainty P* -- forces the filter to accept new evidence with
    higher weight, allowing the estimate to be corrected
  - *Adds the bond to the reward pool* -- amplifying the stakes
  - *In production*: extends the settlement window and increases the required quorum

  Multiple escalation levels can chain, each doubling the previous bond.  This creates
  an exponential cost curve for attackers:

  | Level | Bond multiplier | Cumulative attacker cost |
  |-------+-----------------+--------------------------|
  |     1 | 2x              | 2x                       |
  |     2 | 4x              | 6x                       |
  |     3 | 8x              | 14x                      |
  |     4 | 16x             | 30x                      |

  A lone truth-teller pays once at the level where honest reporters can outvote the
  cartel.  The cartel must pay at every preceding level to maintain their false value.

** False Challenge Penalty

   If a challenger escalates when there is no manipulation (all reporters are honest),
   the challenger's bond enters the reward pool and is distributed to the honest
   reporters.  This prevents griefing via frivolous challenges.

* Game-Theoretic Properties

** Honesty is the Dominant Strategy

   An honest reporter:
   - Earns a share of dishonest reporters' stakes every round
   - Accumulates low R (high Kalman influence) over time
   - Benefits from early submission bonus when they report quickly

   A dishonest reporter:
   - Loses their stake every round (classified as dishonest at settlement)
   - Accumulates high R (the filter learns to ignore them)
   - Faces challenge escalation that amplifies their losses

** Manipulation Requires Sustained Expenditure

   Even with a majority of reporters colluding:
   - A single challenger can escalate, resetting Kalman uncertainty and attracting more
     honest reporters with amplified rewards
   - The colluders must match escalating bonds at every level
   - Their accumulated R means the filter already discounts their submissions
   - Each failed round (where the truth is eventually revealed) costs them their full stakes

** Retroactive Truth Discovery

   The Kalman filter + reputation system creates a form of retroactive truth discovery:
   - If a reporter submits the true value while the majority submits a false one, the
     honest reporter's R stays low (their value was close to the eventual settled value)
   - As more honest reporters join in subsequent rounds, the settled value converges to
     truth, and the early honest reporter's track record is validated
   - This matches the design goal: truth-tellers are rewarded even if initially surrounded
     by liars

  The 37 tests characterize a clear boundary for when TruthStake finds the true value.

** The Critical Boundary

   The oracle reliably finds the true value (error <2%) when:

   - *Honest majority* (h >= a): accurate without any challenge mechanism.  At 4:4 the error
     is 1.32%; at 4:1 it is 0.16%.  The Kalman filter's reputation weighting naturally
     suppresses adversarial submissions.

   - *Honest minority with challenger* (h + 1 >= a): a single challenger rescues every tested
     scenario up to 4:5.  Challenge escalation doubles Kalman P, giving fresh honest
     submissions high Kalman gain to correct the estimate.

   - *Adversary supermajority* (h << a): compromised regardless of challenges.  This is a
     fundamental impossibility: no oracle can extract truth when >2/3 of reporters lie,
     analogous to the Byzantine fault tolerance limit.  However, even in the compromised case,
     the adversaries are *net negative financially* due to warmup losses in the first 3
     rounds when they have high R (untrusted).

   The boundary can be stated concisely: TruthStake finds the true value with probability
   approaching 1 whenever ~honest reporters + willing challengers >= adversaries~.  Below this
   threshold, the estimate degrades but the attack remains unprofitable.

** Attack-Specific Findings

   *Defenses that work automatically* (no challenger needed):

   - *Whale manipulation*: Kalman gain depends on R (reputation), not stake.  A whale staking
     100x gets identical filter influence.  They just lose more money.
   - *Late entry*: new adversaries are gated by low P after established honest history.  A
     +15% bias is silently rejected with zero impact and zero cost.
   - *Front-running*: copying honest consensus and submitting last is the worst-earning
     strategy (-$7.75 vs +$13.59 for first submitter) due to early-bonus decay.
   - *Symmetric sandwich*: equal biases in opposite directions cancel in the Kalman filter.
   - *Oscillation*: alternating bias increases ema_sq_error (raising R) and the
     accuracy_bonus weighting ensures oscillators earn less per round.

   *Defenses that require a challenger*:

   - *Coordinated cartel*: at 3:3, the cartel creates 2.17% error without challenge but is
     restored to 0.95% with one.
   - *Sybil attack*: at 3:5 the oracle is compromised, but 4:5 + challenge restores it.
   - *Gradual drift*: +0.3%/round ramp evades gating (no sudden deviation).  A velocity-based
     challenger comparing 5-round estimate deltas detects and corrects this.

   *Identified weaknesses*:

   - *Sleeper cartel at equal ratio*: 3:3 sleepers with 20 rounds of perfect reputation
     produce only 0.37% peak error -- the equal-R cancellation effect suppresses them.  But at
     higher ratios (5:3) sleepers could be more dangerous.
   - *Brief burst attack*: high-reputation agents who manipulate for 5 rounds and stop can
     gain a small net profit ($22 in the Gold simulation).  This is the one scenario where the
     unchallenged mechanism does not punish the attacker.  An auto-challenge triggered by
     Kalman P spikes would close this gap.
   - *Post-challenge high-P window*: immediately after a legitimate challenge doubles P, an
     opportunistic adversary has higher Kalman gain for 1--2 rounds.  But honest
     re-submissions dilute the effect and the filter recovers within 5 rounds.

* Strengthening Challenges: Double-Down, Retroactive Escrow, and Progressive Escalation

  The current challenge mechanism resets Kalman uncertainty (doubling P) and adds the
  challenger's bond to the pool.  This is effective but has a structural weakness: it only
  affects the *current round*.  An adversary can absorb a single challenge loss and resume
  manipulation in the next round at baseline stakes.  Three extensions make challenges
  significantly more powerful.

** Double-Down Requirement

   When a challenge is raised, *all reporters who submitted in the current round must double
   their stake to keep their submission active*.  Those who decline have their submission
   withdrawn (stake returned, but the submission is removed from the Kalman filter update and
   they forfeit any payout).

   This changes the game theory fundamentally:

   - An honest reporter who submitted the true value has *no reason not to double down* --
     they believe their value is correct and the increased stake just means a larger payout
     when they are vindicated.

   - A dishonest reporter who submitted a biased value now faces a dilemma: double their
     exposure on a lie they know is false, or withdraw and forfeit.  If they double down and
     the challenge attracts more honest reporters, they lose 2x.  If they withdraw, they
     reveal their lack of conviction (which could be tracked as a reputation signal).

   The withdrawal rate after a challenge becomes a powerful manipulation indicator.  In an
   all-honest scenario, nobody withdraws.  If 3 of 6 reporters withdraw after a challenge,
   the remaining 3 (who doubled down) are much more likely to be honest.  The Kalman filter
   can immediately recompute without the withdrawn submissions, and the doubled stakes from
   the remaining reporters amplify the reward pool.

   At escalation level L, the required stake is base * 2^L.  A manipulator who survives all
   levels must have committed 1x + 2x + 4x + ... + 2^L x = (2^(L+1) - 1) x total -- an
   exponential in L, compared to a single challenger bond at each level.

** Retroactive Escrow: Extending the Settlement Window Backward

   A more radical extension: when a challenge is raised, a fraction of *previous rounds'
   payouts* are clawed back into escrow and re-evaluated against the post-challenge settled
   value.

   The mechanism:

   1. Each round, reporters receive only (1 - escrow_fraction) of their payout immediately.
      The remaining escrow_fraction (e.g. 20%) is held for a lookback window of W rounds.

   2. When a challenge is raised in round N, escrowed payouts from rounds N-W through N-1
      are re-evaluated.  For each escrowed payout:
      - If the reporter's past submission is within tolerance of the *newly corrected*
        estimate: the escrow is released to them (they were right all along).
      - If the past submission is now outside tolerance: the escrow is confiscated into the
        current round's reward pool.

   3. After W rounds with no challenge, escrowed funds are released automatically.

   This transforms the economics of several attacks:

   - *Sleeper cartel*: the most dangerous attack is building reputation over 20 rounds, then
     striking.  With retroactive escrow, the cartel members' payouts from those 20 "honest"
     rounds are partially held in escrow.  When their attack is challenged and the estimate
     corrected, their past submissions (which looked honest relative to the *biased* estimate
     they helped create) are re-evaluated against the *corrected* estimate.  If the cartel was
     gradually drifting the estimate even during their "honest" phase, the retroactive check
     catches this.

   - *Gradual drift*: a drifter who moves the estimate 0.3%/round accumulates escrow over W
     rounds.  When a velocity-based challenger finally triggers, the last W rounds of payouts
     are re-checked against the corrected estimate.  The drifter loses not just their current
     stake but their escrowed history.

   - *Brief burst*: the one currently-profitable attack ($22 over 5 rounds) becomes
     unprofitable if the attacker's 30 rounds of pre-burst escrow are at risk.  The burst
     shifts the estimate, which triggers a challenge, which re-evaluates the burst rounds and
     confiscates the escrowed payouts.  Even if the pre-burst submissions were honest, the
     attacker must consider that any manipulation puts their entire escrow at risk.

   - *Majority takeover*: even a supermajority (6:2) that controls the current estimate must
     contend with the fact that a future influx of honest reporters could trigger a challenge
     that re-evaluates their escrowed history.  The longer they maintain the false estimate,
     the more escrow they accumulate that is vulnerable to correction.

** Progressive Challenge Escalation (P Floor)

   The standard challenge doubles P (P *= 2^level), but from a potentially tiny base.
   After 20 rounds of convergence, P might be 0.00006 -- doubling it to 0.00012 is still
   negligible.  Newcomers with R=0.005 get K = 0.00012/(0.00012+0.005) = 0.023, meaning
   their observations barely move the estimate.

   The progressive P floor solves this by guaranteeing a minimum P on challenge:

   #+begin_example
   Level 1: P >= challenge_P_floor          (e.g. 0.01)
   Level 2: P >= challenge_P_floor * 2      (e.g. 0.02)
   Level 3: P >= challenge_P_floor * 4      (e.g. 0.04)
   Level N: P >= challenge_P_floor * 2^(N-1)
   #+end_example

   With P=0.01 after a level-1 challenge, a newcomer's K = 0.01/(0.01+0.005) = 0.67 --
   their observations have real influence.  Each successive challenge opens the filter wider,
   reflecting increasing uncertainty about the entrenched estimate.

   This is the key mechanism that breaks the *reputation circular dependency*: when liars
   control the oracle for many rounds, their R drops to ~0.0001 (the filter trusts them)
   while newcomers start at R=1.0.  Without the P floor, even a numeric majority of honest
   newcomers cannot shift the estimate because K is negligible for everyone.  The P floor
   resets the playing field so that accuracy, not incumbency, determines influence.

   Simulation results confirm:
   - Without P floor: 20-round liar control (6:2) followed by 10:6 honest influx -- liars
     net +622, estimate stays biased at +7.7%.
   - With P floor=0.01: same scenario -- liars go net negative, estimate corrects.
   - Progressive escalation: 3 challenges produce P=0.04, giving newcomers K=0.89 and
     near-complete correction in a single round.

** Combined Effect: The Conviction Curve

   With both mechanisms, the cost of sustained manipulation follows a "conviction curve":

   #+begin_example
   Round N:   Submit biased value, stake S
   Challenge: Must double-down to 2S or withdraw (revealing lack of conviction)
   Round N+1: Submit again at base stake, but 20% of winnings held in escrow
   Round N+W: If no further challenge, escrow from round N+1 released
              If challenged: escrow re-evaluated, potentially confiscated
   #+end_example

   The total capital at risk for a manipulator is not just their current stake but:

   #+begin_example
   Current exposure = current_stake * 2^(escalation_level)
                    + SUM(escrow[round] for round in N-W..N-1)
   #+end_example

   For an honest reporter, this is irrelevant: their past submissions were truthful, so
   retroactive re-evaluation confirms them.  Their escrow is always released.  For a
   manipulator, every round of "successful" manipulation accumulates escrow that a single
   future challenge can confiscate.

   This creates what might be called a *conviction asymmetry*: honest reporters can
   double-down indefinitely at zero expected cost (they are right), while dishonest reporters
   face compounding exposure with every round they maintain the lie.  The longer a
   manipulation persists, the more profitable it becomes to challenge -- exactly the opposite
   of what the attacker needs.

** Impact on the Critical Boundary

   With these extensions, the boundary for truthful oracle operation shifts:

   - Without extensions: truth requires ~honest + challengers >= adversaries~
   - With double-down: the withdrawal signal allows the Kalman filter to self-correct by
     removing low-conviction submissions.  This effectively reduces the adversary count by
     the number who withdraw, shifting the ratio toward honest.
   - With retroactive escrow: the effective cost of manipulation multiplies by ~1 + W *
     escrow_fraction~, because each round of manipulation puts not just the current stake but
     accumulated escrow at risk.  A 20% escrow with W=10 means each manipulation round risks
     an additional 2x (10 * 0.2) beyond the current stake.  This makes even brief burst
     attacks unprofitable and forces supermajority attackers to consider whether they can
     maintain control indefinitely -- because losing it even once triggers retroactive losses.

   The combined effect is that the threshold for truthful operation moves from ~50% honest~ to
   something significantly lower, because the mechanisms convert *duration of attack* into
   *accumulated financial exposure*.  An adversary who controls 60% of reporters might be
   able to bias the estimate, but cannot sustain it indefinitely without accumulating escrow
   that a future challenge can confiscate.  The oracle's integrity guarantee becomes: *truth
   will be found whenever there exists a future round in which honest reporters + challengers
   can establish a majority, even briefly*.

* Consumer Feed Fees: Demand-Side Revenue

  The FeedOracle adds a demand-side revenue model: consumers (smart contracts, DeFi
  protocols) pay a per-read fee that flows into the next round's reward pool.

** Revenue Model

   - *Base feed fee*: paid per read, accumulates until the next round opens, then flushed
     into that round's reward pool.
   - *Uncertainty premium*: when Kalman P exceeds a configurable threshold, the fee is
     multiplied (default 3x).  Consumers pay more when the oracle is uncertain, which funds
     the increased reporting effort needed to reduce uncertainty.
   - *Consumer challenge bonds*: non-reporters can post bonds to trigger escalation without
     having a reporter identity.  The bond enters the reward pool and doubles P, just like
     a reporter challenge.

** Positive Externality Loop

   More consumers reading -> larger reward pool -> more reporters attracted by higher
   rewards -> more accurate estimates -> more consumers trust the oracle -> more reads.

   Simulation results (30 rounds):
   - 2 consumers, 2 reporters: small pool, moderate accuracy
   - 20 consumers, 6 reporters: 10x larger pool, better accuracy, 3x reporter earnings

   The uncertainty premium creates a natural feedback: uncertain periods generate more
   revenue, which funds the additional reporting effort needed to resolve the uncertainty.

** Game-Theoretic Impact

   Feed fees make honest reporting *strictly dominant* regardless of adversary count.
   Without fees, a reporter's expected return depends on the number of dishonest reporters
   present (honest reporters need dishonest ones to have positive P&L).  With feed fees,
   honest reporters profit even in an all-honest scenario because consumer revenue
   supplements the stake-based pool.

   At moderate fee levels (2.0 per read, 5 reads/round):
   - Honest ROI: positive and increasing with fee level
   - Liar ROI: negative and unaffected by fee level
   - The gap widens with higher fees, making manipulation increasingly irrational

** Consumer-Funded Correction

   During manipulation, consumers who detect bias (e.g., by comparing the oracle to
   their own reference prices) can fund correction directly via consumer challenge bonds.
   Three consumer challenges at escalating bonds (10, 20, 40) fund the P reset needed for
   honest reporters to correct a 15-round bias -- the correction is funded by the consumers
   who benefit from oracle accuracy, not just by competing reporters.

   | Retroactive confiscation |     2 | Liar escrow confiscated on challenge, honest escrow survives             |
   | Non-ergodic collapse     |     7 | Honey pot grows, honest influx triggers collapse, progressive escalation |
   | Feed fees                |     6 | Fee-funded pool, uncertainty premium, consumer challenges, game theory   |

   The non-ergodic collapse tests confirm:
   - Honey pot grows monotonically during liar control (20x over 20 rounds)
   - P floor enables honest influx to correct biased estimate (liars go net negative)
   - Longer liar control -> larger collapse (30 rounds confiscation > 10 rounds)
   - Brief attacks (3 rounds) are unprofitable without honey pot buildup
   - Liars deplete capital over 80 rounds; honest capital grows
   - Single challenge with P floor flips outcome from biased to accurate
   - Progressive escalation: each challenge level widens the filter further

    *Rounds 4--10: Liars build trust.*  Liars' R drops rapidly (EMA alpha=0.5 during warmup,
    then 0.3).  Because their biased values are consistent with each other and they control
    the settled value, their squared relative error is tiny -- they look "honest" to the
    reputation system.  By round 10, liar R ~= 0.001 vs honest R ~= 0.005.  The estimate
    accelerates upward past $3000.  The two honest reporters are now classified "dishonest"
    relative to the biased consensus and begin losing their stakes.  P collapses below
    0.001 as the filter becomes confident in the wrong answer.

    *Rounds 11--19: Full liar control.*  The estimate stabilizes near $3121 (+7.6% error).
    P is tiny (~0.00006) -- the filter is maximally confident.  Liars collect payouts every

    their stake every round.  But 25% of every payout is withheld in escrow.  The honey pot
    grows monotonically: $10, $30, $50, $80...  The liars' cumulative P&L reaches +$5 while
    honest reporters sit at -$5.  The system looks stable, but the escrow ledger is quietly
    accumulating evidence of the liars' biased submissions alongside the true prices.

    *Round 20: The tipping point.*  Eight newcomers and a challenger arrive, seeing the $80

    for newcomers jumps from K=0.012 (negligible) to K=0.67 (dominant).  Their observations
    of the true price at $2900 yank the estimate downward.

    *Rounds 20--24: Rapid correction under sustained challenge.*  Challenges fire every
    round during this phase, each one escalating the P floor further (0.01, 0.02, 0.04...).
    The honest 10:6 majority now has real influence.  The estimate plunges from $3121 toward
    $2900.  Error drops from 7.6% to below 1% within 5 rounds.  Meanwhile, retroactive
    confiscation activates: the escrowed liar payouts from rounds 0--19 are re-evaluated
    against the stored ground truth.  The liars' submissions ($3132) are now clearly wrong
    relative to the true price ($2900).  Their escrow is confiscated and redistributed to
    the current round's honest reporters.  The liar P&L line (red) plummets.

    *Rounds 25--44: New equilibrium.*  The estimate settles at $2900 (0.01% error).  Liars
    continue submitting +8% bias but are now classified "dishonest" every round, losing
    their stakes to the honest majority.  Challenges fire periodically to maintain the P
    floor.  The honey pot continues to grow (new escrow from ongoing rounds), now filled
    primarily with honest reporters' escrowed payouts -- which will be released cleanly

** Scenario 3: Sleeper Cartel with Challenge

   The most dangerous attack: three cartel members report honestly for 20 rounds (building
   reputation and low R), then suddenly begin reporting +8% biased values.  Because they
   have good track records, their initial attack rounds pull the estimate before the
   Kalman filter has time to inflate their R.

   A challenger monitors for outliers and triggers challenge escalation when any submission
   deviates more than 2 sigma from the current estimate.  The challenge doubles Kalman
   uncertainty P, giving fresh honest submissions more weight to correct the estimate.

   #+begin_src python :session truthstake :results value
     oracle = Oracle(initial_estimate=prices[0], Q=0.0005, min_stake=10.0, tolerance=0.03)

     honest = []
     for i in range(3):
         r = Reporter(f"honest_{i}", stake=100000)
         oracle.register(r)
         honest.append(r)

     cartel = []
     for i in range(3):
         r = Reporter(f"cartel_{i}", stake=100000)
         oracle.register(r)
         cartel.append(r)

     challenger = Reporter("challenger", stake=100000)
     oracle.register(challenger)

     rng = random.Random(42)
     attack_start = 20
     n_challenges = 0

     for rid, price in enumerate(prices):
         oracle.open_round()
         bias = 0.0 if rid < attack_start else 0.08

         all_subs = []
         for r in honest:
             all_subs.append((r, price * (1 + rng.gauss(0, 0.003))))
         for r in cartel:
             noise = rng.gauss(0, 0.002) if rid < attack_start else 0.0
             all_subs.append((r, price * (1 + noise + bias)))
         all_subs.append((challenger, price * (1 + rng.gauss(0, 0.003))))

         rng.shuffle(all_subs)
         for r, v in all_subs:
             try:
                 oracle.submit(r, v, stake=10.0)
             except ValueError:
                 pass

         # Challenge detection
         if rid >= 3:
             est = oracle.kalman.x
             P = oracle.kalman.P
             sigma = math.sqrt(P) if P > 0 else 0
             for sub in oracle.current_round.submissions:
                 z = oracle._normalize(sub.value)
                 if sigma > 0 and abs(z - est) > 2.0 * sigma:
                     try:
                         oracle.challenge(challenger)
                         n_challenges += 1
                         for r in honest:
                             try:
                                 oracle.submit(r, price * (1 + rng.gauss(0, 0.003)), stake=10.0)
                             except ValueError:
                                 pass
                         try:
                             oracle.submit(challenger, price * (1 + rng.gauss(0, 0.003)), stake=10.0)
                         except ValueError:
                             pass
                     except ValueError:
                         pass
                     break

         oracle.settle(true_price=price)

     c_net = sum(r.earnings - r.losses for r in cartel)
     h_net = sum(r.earnings - r.losses for r in honest)
     ch_net = challenger.earnings - challenger.losses

** Cost of Manipulation vs. Cost of Defense

   The asymmetry between attack cost and defense cost is the fundamental security property.
   A manipulator must pay at every round they attack; a challenger pays once.

   | Stake/round | Attack duration | Attacker total cost | Challenger bond | Ratio |
   |-------------+-----------------+---------------------+-----------------+-------|
   |         $10 | 5 rounds        |                 $50 |             $20 |  2.5x |
   |         $10 | 15 rounds       |                $150 |             $20 |  7.5x |
   |         $10 | 75 rounds       |                $750 |             $20 | 37.5x |
   |         $50 | 15 rounds       |                $750 |            $100 |  7.5x |

   At 15 rounds of sustained manipulation, the attacker spends 7.5x what a single
   challenger needs to trigger escalation.  At 75 rounds (the full simulation), the
   ratio is 37.5x.  The longer the attack persists, the more economically irrational it
   becomes -- and the more profitable it becomes for honest reporters.

* Research: How Oracles Handle Truth, Time, and Lies

  A survey of every major deployed oracle reveals a universal limitation: *none allows
  retroactive correction of historical values once confirmed*.  Every system treats
  published data as immutable after a short finality window.  This section summarizes the
  landscape and identifies what TruthStake can do differently.

** Oracle Categories

   Every oracle falls into one of three categories:

   1. *Market-derived* (trustless, no reporters): Uniswap TWAP, Curve, Balancer.  Data comes
      from on-chain trades.  No reporters means no liars -- but also no way to price assets
      without active trading pools (commodities, off-chain assets).

   2. *Trusted operators* (permissioned reporters): Chainlink, Chronicle, API3.  A whitelisted
      set of node operators publishes data.  Trust is in operator selection, not economic
      incentives.

   3. *Open participation* (permissionless reporters): Tellor, UMA, Flare FTSO, Pyth, and
      what TruthStake proposes.  Anyone can report, and economic mechanisms must distinguish
      truth from lies.

** Uniswap V3/V4 TWAP

   The only deployed oracle with genuine time-series data.  A ring buffer of up to 65,535
   observations stores ~tick * time_elapsed~ accumulators, enabling geometric-mean TWAP
   computation over any window within the buffer.  One observation per block, deterministic
   from swap state.

   - *Strengths*: Trustless, manipulation-resistant over long windows, real temporal curve.
   - *Liar detection*: N/A -- observations are deterministic from trades.
   - *Correction*: Impossible.  Append-only ring buffer.  A manipulated price stays until
     overwritten.
   - *Limitation*: Only prices assets with active on-chain pools.  Cannot price Gold, Silver,
     agricultural products, or any off-chain commodity.  Post-Merge multi-block MEV (validator
     controlling consecutive slots) can corrupt observations with zero arbitrage risk during
     their slots.

** Chainlink

   Permissioned set of up to 31 whitelisted nodes aggregate off-chain via OCR (Off-Chain
   Reporting), publishing a median answer on-chain.  Historical data accessible via
   ~getRoundData(roundId)~ -- but this is a log of publications, not a curated time-series.

   - *Liar detection*: Off-chain and opaque.  Deviant nodes identified by Chainlink's
     centralized monitoring.  ~Flags.sol~ provides a permissioned circuit-breaker.
   - *Correction*: None.  Published answers are immutable.  During the LUNA crash, Chainlink
     froze the feed at $0.10 rather than publish the true ~$0.00001 price.  Consumer
     protocols must implement their own staleness checks.
   - *Limitation*: Trust is in node selection by Chainlink Labs.  No on-chain penalty for
     incorrect values.  Deviation-threshold + heartbeat update model means on-chain price can
     be stale between updates.

** UMA (Optimistic Oracle)

   Closest to TruthStake's challenge model.  A proposer stakes a bond and asserts an answer.
   During a ~2-hour dispute window, anyone can dispute by posting a matching bond.  Disputes
   escalate to the DVM (Data Verification Mechanism) -- a Schelling-point vote by UMA token
   holders.

   - *Liar detection*: Dispute window + DVM vote.  Proposer loses bond if dispute succeeds.
   - *Correction*: Only during the dispute window.  Once the window closes, the value is final
     and immutable.  No retroactive correction, no forward propagation.
   - *Limitation*: Resolves individual price requests, not time-series.  The DVM vote is a
     Schelling point (incentivized to vote with majority, not with truth).  No accuracy
     weighting or reputation -- influence is proportional to token holdings.

** Tellor

   Permissionless stake-to-report model.  Reporters stake TRB tokens and submit values.
   Anyone can dispute within a 12-hour window, triggering a 2-day token-holder vote.

   - *Liar detection*: Dispute + slash.  If dispute succeeds, reporter's stake is slashed
     (half to disputer, half burned).  Multiple voting rounds with escalating thresholds.
   - *Correction*: Only during the dispute window.  Disputed values are marked and skipped,
     not corrected in place.  No propagation of corrections through subsequent values.
   - *Limitation*: In 2023, Tellor was exploited on Polygon because the dispute window was
     shorter than the L1-L2 bridge delay -- an attacker submitted a false value and used it
     before anyone could dispute cross-chain.  Fundamental fragility of fixed dispute windows.

** Pyth Network

   ~80 first-party publishers (exchanges, market makers) submit ~(price, confidence)~ pairs.
   Aggregated via weighted median.  Full history stored off-chain on Pythnet; only the latest
   attested price is stored on-chain.

   - *Liar detection*: Implicit.  Publishers that disagree widen the aggregate confidence
     interval.  Off-chain weight reduction by governance.
   - *Correction*: None.
   - *Innovation*: The confidence interval is the closest any production oracle comes to
     Kalman P.  But it is a static aggregation metric (how much publishers disagree right
     now), not a dynamically evolving uncertainty estimate.

** Flare FTSO (Time Series Oracle)

   Despite the name, does not maintain a time-series.  Produces a single price per 3-minute
   epoch via commit-reveal + weighted median.  Providers within the IQR reward band receive
   inflationary rewards; those outside receive nothing (but are not slashed).

   - *Liar detection*: Reward exclusion only.  No slashing, no dispute.
   - *Correction*: None.  Each epoch is final.
   - *Limitation*: The reward band creates a Schelling-point vulnerability -- providers are
     incentivized to submit near the median of *other providers*, not near the true value.
     A majority cartel shifts the band center.

** Prediction Markets (Augur, Polymarket)

   Resolve discrete events (not continuous price feeds).  Augur has the most sophisticated
   dispute mechanism: multi-round escalation with doubling bonds, ending in a fork of the
   REP token at the maximum dispute level.

   - *Correction*: Yes, but only for event outcomes, and only before final settlement.
     Not applicable to continuous time-series.
   - *Relevance*: The dispute escalation model (exponentially increasing bonds) is a direct
     precedent for TruthStake's challenge mechanism.

** The Universal Gap

   | Capability                    | Uniswap  | Chainlink | UMA    | Tellor | Pyth      | FTSO        | Augur  |
   |-------------------------------+----------+-----------+--------+--------+-----------+-------------+--------|
   | Time-series data              | Ring buf | Round log | No     | Log    | Off-chain | No          | No     |
   | Retroactive correction        | No       | No        | Window | Window | No        | No          | Window |
   | Accuracy-weighted aggregation | N/A      | Median    | Vote   | Vote   | Wt med    | Wt med      | Vote   |
   | Uncertainty quantification    | No       | No        | No     | No     | Conf      | No          | No     |
   | Correction propagates forward | No       | No        | No     | No     | No        | No          | No     |
   | Liar P&L consequence          | N/A      | Removal   | Bond   | Slash  | Wt red    | Reward excl | Bond   |
   | Deferred settlement           | N/A      | No        | 2 hr   | 12 hr  | No        | No          | Weeks  |

   No deployed oracle:
   - Allows retroactive correction of historical values after the dispute window closes
   - Propagates corrections forward through subsequent values when history is revised
   - Uses accuracy-weighted signal extraction (all use median or Schelling-point voting)
   - Models uncertainty dynamically (Pyth's confidence interval is the closest attempt)
   - Creates non-ergodic economics where the cost of sustained lying compounds over time

* TruthStake V2: Time-Series Oracle with Deferred Settlement

  The research above reveals that what is needed -- a time-series oracle where historical
  values can be challenged, corrections propagate forward, and reporters are paid against the
  *final* consensus curve -- does not exist.  This section proposes an architecture.

** What the Oracle Represents

   An accurate time-value curve ~f(t)~ for a tracked variable (Gold price, exchange rate,
   temperature).  Not just "what is the price now" but "what was the price at every past
   moment, and how confident are we in each point."

   This matters because financial products depend on *derivatives* of the curve: rate of
   return, volatility, moving averages.  An oracle that gets the instantaneous price right
   but distorts the shape of the curve (e.g., smoothing over a flash crash, or introducing a
   phantom spike) corrupts every product that computes on the history.

** Core Data Model

   The oracle maintains a *time-indexed curve* rather than a single scalar estimate:

   #+begin_example
   TimeSlot {
       timestamp:       uint64        -- epoch seconds (e.g., 1741798800 = 2025-03-12 15:00 MT)
       estimate:        int256        -- Kalman-smoothed best estimate at this timestamp
       P:               uint256       -- uncertainty (variance) at this timestamp
       submissions:     Submission[]  -- all (reporter, value, stake) for this slot
       challenges:      Challenge[]   -- any challenges targeting this slot
       finalized:       bool          -- true once the challenge window has expired
       finalized_at:    uint64        -- block timestamp when finalization occurred
   }
   #+end_example

   Slots are indexed by ~(asset_id, timestamp)~.  A Gold oracle with hourly resolution has
   one slot per hour; daily resolution has one per day.  The resolution is a parameter of the
   oracle instance.

** Submission Lifecycle: Three Phases

*** Phase 1: Open Submission Window

    For each time slot, there is a window during which reporters can submit observations at
    base stake.  For an hourly oracle:

    #+begin_example
    Slot timestamp:     2026-03-12 15:00 MT
    Submission window:  15:00 -- 15:30 MT (30 minutes after the slot)
    #+end_example

    During this window, reporters submit ~(timestamp, value, stake)~ tuples.  Each submission
    updates the Kalman filter for that slot, weighted by the reporter's R (reputation).  The
    early-submission bonus rewards speed and conviction -- the first reporter to submit an
    accurate value for a slot earns the most.

    Submissions for the *current* slot are cheap (base stake).  Submissions for *recent past*
    slots (within a lookback window) are allowed at higher cost -- the further back, the more
    expensive, because late submissions signal either tardiness or attempted manipulation.

*** Phase 2: Challenge Window

    After the submission window closes, the slot enters a challenge window:

    #+begin_example
    Challenge window:   15:30 -- 16:30 MT (1 hour after submission closes)
    #+end_example

    During this window, anyone (reporters, consumers, automated monitors) can challenge the
    slot's estimate by posting a bond.  A challenge:

    1. Resets Kalman P for the challenged slot to at least the P floor (progressive
       escalation: each successive challenge level doubles the floor).
    2. Reopens the slot for new submissions at escalated stake.
    3. Triggers *forward re-projection*: if the challenged slot's estimate changes
       materially, all subsequent slots' estimates are recomputed using the corrected
       history (see "Kalman Smoother" below).

    Challenging an *older* slot (one that has already passed through its normal challenge
    window but has not yet been finalized due to a downstream challenge) costs more:

    #+begin_example
    Challenge bond = base_bond * 2^level * age_multiplier(slot_age)
    age_multiplier = 1 + (slot_age / resolution)
    #+end_example

    A challenge at the current slot costs base_bond * 2.  A challenge targeting a slot 6
    hours old (6 slots back on an hourly oracle) costs base_bond * 2 * 7 = 14x base.

*** Phase 3: Finalization and Settlement

    A slot is finalized when its challenge window expires *and* no active challenge has
    propagated corrections through it.  At finalization:

    1. The slot's estimate becomes the official value for that ~(asset, timestamp)~ pair.
    2. Reporters are classified honest/dishonest against the *finalized* estimate -- not the
       instantaneous estimate at submission time.
    3. The reward pool (all stakes + all challenge bonds + accumulated feed fees) is
       redistributed to honest reporters, weighted by accuracy and submission order.
    4. Dishonest reporters lose their stakes and have their R (reputation) inflated.
    5. A fraction of payouts is held in escrow for W additional slots.

    This deferred settlement eliminates the circular dependency in the current implementation:
    reporters are never judged against a value that liars control.  The finalized value
    incorporates all evidence from the submission window, the challenge window, and any
    re-projections from corrections to earlier slots.

** Kalman Smoother: Forward-Backward Estimation

   The current implementation uses a forward-only Kalman filter: each ~update()~ incorporates
   one observation and moves on.  A time-series oracle needs a *smoother* that incorporates
   evidence from both directions.

*** Why Forward-Only Fails

    In a forward-only filter, the estimate at slot T uses only observations from slots
    0..T.  If slot T+5 reveals that slot T was wrong (via a challenge), there is no mechanism
    to propagate that information backward.

*** Rauch-Tung-Striebel (RTS) Smoother

    The standard solution: run the Kalman filter forward to accumulate all observations (the
    "forward pass"), then run backward from the final slot to propagate future evidence into
    past estimates (the "backward pass").  This gives the maximum-likelihood estimate at
    every timestamp given *all* observations, not just past ones.

    #+begin_example
    Forward pass (standard Kalman):
        For each slot t = 0, 1, ..., N:
            predict: x_pred(t) = x(t-1), P_pred(t) = P(t-1) + Q
            For each submission z at slot t:
                K = P_pred / (P_pred + R_reporter)
                x(t) = x_pred + K * (z - x_pred)
                P(t) = (1 - K) * P_pred

    Backward pass (RTS smoother):
        For each slot t = N-1, N-2, ..., 0:
            G(t) = P(t) / P_pred(t+1)
            x_smooth(t) = x(t) + G * (x_smooth(t+1) - x_pred(t+1))
            P_smooth(t) = P(t) + G * (P_smooth(t+1) - P_pred(t+1)) * G
    #+end_example

    The backward pass is O(N) in the number of slots and requires only the forward-pass
    state at each slot (stored in the TimeSlot structs).  It does not need to re-process
    individual submissions.

*** When to Re-Smooth

    Re-smoothing is triggered by any event that materially changes a slot's evidence:
    - A new submission during a reopened challenge window
    - A challenge that resets P for a historical slot
    - Finalization of a challenged slot (freezes its estimate, triggering a final re-smooth
      of downstream slots)

    Re-smoothing only needs to run from the modified slot forward to the latest slot.  It
    does not need to re-run the entire history.

*** On-Chain Feasibility

    The RTS smoother requires storing ~(x, P, x_pred, P_pred)~ per slot.  For an hourly
    oracle with 30-day lookback: 720 slots * 4 uint256 = 2,880 storage words.  This is
    practical on-chain.

    The backward pass is O(N) multiplications per re-smooth.  For N=720, this is ~2,880
    multiplications -- well within a single transaction's gas budget.  Challenge-triggered
    re-smoothing can be bounded by only re-projecting forward from the challenged slot to
    the current slot.

** Challenge Economics: Age-Scaled Non-Ergodic Costs

*** Why Age Matters

    Challenging a recent slot is cheap because the disruption is local: only a few
    downstream slots need re-projection.  Challenging an old slot is expensive because:

    1. Many downstream slots must be re-projected (gas cost).
    2. Many settlements may need to be reversed or adjusted (economic disruption).
    3. The evidence for old slots should be strong (many reporters have already confirmed it).

    But this cost must be balanced: if challenging old slots is *too* expensive, liars can
    corrupt early slots and escape correction.  The non-ergodic property requires that
    the *reward* for successfully challenging an old corrupted slot also scales with age.

*** The Honey Pot Mechanism (Preserved from V1)

    Escrow from all unsettled slots since the corrupted one becomes the challenge reward.
    If liars controlled slots T through T+20, there are 21 slots' worth of escrow at stake.
    The longer the corruption persists, the larger the honey pot, and the more attractive it
    becomes to mount an expensive historical challenge.

    #+begin_example
    Challenge cost:   base_bond * 2^level * (1 + age_in_slots)
    Challenge reward: escrow from all slots in [challenged_slot, current_slot]
                      that are re-evaluated and found to contain liar payouts
    #+end_example

    For a 20-slot corruption: the challenger pays ~21x base bond.  If successful, they
    receive confiscated escrow from 21 slots' worth of liar payouts.  With 25% escrow
    fraction and 8 reporters per slot at $2 stake: 21 * 0.25 * 8 * $2 = $84 in confiscable
    escrow.  The challenge bond of 21 * $4 = $84 is roughly break-even -- which means the
    challenge is free when it succeeds.  Any additional escrow from inflated pools (due to
    challenge bonds and feed fees entering the pool) makes the challenge profitable.

*** Non-Ergodic Dynamics (Preserved and Strengthened)

    The V1 honey-pot dynamics carry over directly:

    1. Liars controlling the oracle accumulate escrow that is vulnerable to correction.
    2. The longer they maintain control, the larger the honey pot.
    3. The honey pot attracts challengers and honest reporters.
    4. A single successful challenge triggers retroactive confiscation across all corrupted
       slots, not just the challenged one.
    5. The RTS smoother propagates the correction forward, causing liars in downstream slots
       to be reclassified as dishonest.

    The new element: because the smoother propagates corrections *forward*, a successful
    challenge at slot T can cause reclassification of reporters in slots T+1, T+2, ..., up
    to the current slot.  This means the total confiscation from a single challenge can be
    vastly larger than the challenge bond -- the non-ergodic trap is even more severe than
    in V1.

** Consumer Feed Fees (Preserved from V1)

   Consumers pay per-read fees that flow into the next slot's reward pool.  The uncertainty
   premium (higher fees when P is large) is now richer: P varies across the time-series, so
   consumers pay more to read uncertain slots and less for well-established ones.

   Consumer challenges are unchanged: a non-reporter posts a bond targeting a specific
   ~(asset, timestamp)~ slot, triggering escalation and re-smoothing.

** Reporter Experience

*** Normal Operation

    A reporter observes the Gold price at 15:00 MT, submits ~(Gold, 1500MT, $2905, $2 stake)~
    within the 30-minute window.  If their value agrees with the finalized estimate (after
    all challenges expire), they receive their stake back plus a share of dishonest reporters'
    stakes and feed fees.  They are paid ~1 hour after submission (submission window +
    challenge window).

*** Late Submission

    The reporter missed the 15:00 MT window but has evidence that the published value is
    wrong.  They submit for the 15:00 slot during the challenge window at elevated cost (the
    slot must be challenged first, or their submission arrives as part of a challenge).  If
    they are right, they earn the challenger's reward.

*** Historical Correction

    The reporter notices that the 11:00 MT value (4 hours ago, 4 slots back) appears
    incorrect.  They fund a challenge targeting the 11:00 slot, paying ~5x base bond (age
    multiplier).  The challenge reopens the slot, resets its P to the floor, and the reporter
    submits their corrected value.  If the re-smoothed estimate shifts materially, all
    downstream slots are re-projected.  If the correction is validated by finalization, the
    reporter earns confiscated escrow from the corrupted slots.

* V3 Rethink: Stake-Weighted Mode vs. Kalman Filtering

  The V2 implementation revealed a fundamental tension between Kalman filtering and
  the oracle's actual use case.

** The Smoother Manipulation Attack

   An attacker who has placed bets on slot T can retroactively place bets on slot T-1
   or T-2 that cause the RTS smoother to bend the curve through their slot T position.
   The retroactive bets may be "wrong" in the sense that they don't match the true
   value at T-1 -- but they're strategically placed so the smoothed curve passes
   closer to the attacker's T position, winning them a larger share of the pool.

   This is inherent to any averaging estimator: the estimate at one time depends on
   observations at other times.  An attacker who understands the smoother's math can
   game the cross-temporal dependency.

** Two Kinds of Oracle Problem

   Kalman filtering solves the wrong problem for most oracle use cases:

*** Noisy Independent Measurements

    Multiple observers each measure a hidden true value with Gaussian error.
    Temperature from 20 sensors.  Commodity spot price from 5 exchanges with
    different spreads and latency.  The true value is unknown; a weighted average
    is the maximum-likelihood estimate.

    *Kalman is ideal here.*  The filter extracts signal from noise, and reputation-
    weighted R ensures proven-accurate reporters dominate the estimate.

*** Deterministic Published Values

    The true value is a *known fact*: COMEX Gold close, Bank of Canada rate, CPI
    release.  There is no measurement noise.  The only question is whether each
    reporter is telling the truth or lying.

    *Kalman is wrong here.*  There is no hidden state to estimate.  An average of
    "2905.30" (truth) and "3000.00" (lie) is "2952.65" -- wrong.  The correct
    answer is "2905.30" because more honest reporters agree on it.  The **mode**
    (most commonly posted value) is the right estimator.

    Most of what the Alberta Buck needs falls into this category.

** Why Not Median or Mean

   - *Mean / Kalman*: a single large outlier shifts the estimate.  An attacker with
     enough stake can move the settled value continuously.  Cross-temporal smoothing
     creates secondary manipulation surfaces.

   - *Median*: better than mean (robust to outliers) but still allows manipulation
     by controlling the distribution's center.  A Sybil attack placing many values
     just above/below the true value shifts the median without triggering outlier
     detection.

   - *Mode*: the attacker must match or exceed the count of the most popular value.
     For published values with a single correct answer, all honest reporters post
     the same number.  The attacker needs >50% of total posts (not stake, not
     influence -- raw count) to override, making Sybil the primary attack vector.

** Stake-Weighted Mode: The Right Estimator

   Combine mode selection with stake weighting to resist both Sybil and capital
   attacks:

   #+begin_example
   For each slot:
     1. Group submissions by value (exact match, or within a precision epsilon)
     2. For each group, compute total_stake = sum of stakes in that group
     3. The winning value = the group with the highest total_stake
     4. All reporters in the winning group share the losers' stakes
   #+end_example

   This is a *Schelling point game* with economic teeth:

   - *Honest equilibrium*: everyone posts the true value (the obvious Schelling
     point for a published fact), forming one large group.  Any liar's stake is
     forfeited to this group.

   - *Attack cost*: to override the honest group, the attacker needs
     ~total_attacker_stake > total_honest_stake~ for the slot.  This is a pure
     capital war with no cross-temporal amplification.

   - *No smoothing artifacts*: each slot settles independently.  No retroactive
     manipulation of historical slots can bend the current slot's outcome.

   - *Flash crashes preserved*: if the true value crashed, all honest reporters
     post the crash value.  No smoother dampens it.

** What Carries Forward from V1/V2

   The stake-weighted mode approach preserves the core TruthStake economics:

   - *Challenge escalation*: challenges reopen the slot for new submissions at
     higher stake, attracting more honest capital.  Each challenge level multiplies
     the minimum stake, making defense exponentially more expensive for attackers.

   - *Non-ergodic honey pot*: escrow from liar-controlled slots accumulates.  When
     a challenge flips a slot, the escrowed stakes from the attacker's winning
     period are confiscated and redistributed.  The longer the attack, the larger
     the pot, the more attractive the defense.

   - *Early submission bonus*: the first reporter to post the correct value earns
     the most.  This incentivizes speed and conviction over waiting to copy.

   - *Deferred settlement*: reporters are paid after the challenge window expires,
     not at submission time.  This eliminates the circular dependency.

   - *Block-indexed slots with circular buffer*: slots are indexed by Ethereum
     block number; only the challenge-window-depth of slots are stored on-chain.

   - *Age-scaled challenge bonds*: challenging older slots costs more but unlocks
     more escrowed rewards.

   - *Consumer feed fees*: per-read fees flow into the next slot's reward pool.

** What Changes

   | Aspect                   | V2 (Kalman + RTS)                       | V3 (Stake-Weighted Mode)                    |
   |--------------------------+-----------------------------------------+---------------------------------------------|
   | Estimator                | Weighted average (Kalman filter)        | Stake-weighted mode (most-staked value)      |
   | Cross-slot dependency    | RTS smoother propagates corrections     | Slots settle independently                  |
   | Manipulation surface     | Temporal + weighting                    | Capital only (pure stake war)                |
   | Reporter reputation      | R = EMA of squared error (low R = more  | Not needed (mode doesn't weight by trust)    |
   |                          | influence on average)                   |                                              |
   | Sybil resistance         | Reputation system (new R = high)        | Stake requirement (each submission costs)    |
   | Precision                | Continuous (any value)                  | Discrete (value groups within epsilon)       |
   | Forward propagation      | Smoother re-projects corrections        | Not applicable (slots are independent)       |
   | Ideal for                | Noisy measurements (temperature)        | Published values (commodity close, CPI)      |

** The Precision Epsilon Problem

   For the mode to work, submissions must be grouped.  "2905.30" and "2905.31" are
   the same value to 4 significant figures.  The oracle needs a precision parameter:

   #+begin_example
   epsilon = 0.01%   (4 significant figures)
   group_key = round(value / epsilon) * epsilon
   #+end_example

   This means reporters must agree to within epsilon -- effectively quantizing the
   value space.  For published financial values with exact prices, this is natural.
   For noisy measurements, epsilon must be wider, which reduces the mode's ability
   to distinguish close values.

   This is a feature, not a bug: the oracle's resolution matches the precision of
   the underlying data.

** Open Questions

   - *Hybrid approach*: could the oracle use mode for "published value" assets and
     Kalman for "noisy measurement" assets, selected per asset registration?

   - *Value precision*: how does epsilon interact with different asset types?  Is
     0.01% always right, or should it be configurable per asset?

   - *Tie breaking*: what happens when two value groups have exactly equal total
     stake?  Options: earliest-submitted group wins (preserves early bonus),
     round is voided and stakes returned, or a challenge is auto-triggered.

   - *Continuous values*: for assets without a single published price (e.g., OTC
     commodities, real estate indices), is the mode appropriate at all, or should
     these use a different oracle mechanism?

* V4: Identity-Bound Oracles with Competitive Forking

  V1-V3 assumed anonymous, adversarial reporters and tried to force honesty through
  internal mechanism design: staking, Kalman weighting, mode voting.  The Alberta
  Buck's architecture makes a stronger assumption available: *participants are
  identified, their track record is permanent, and dishonesty has consequences
  across the entire ecosystem, not just within the oracle.*

  This changes everything.

** The Buck Identity Foundation

   The Alberta Buck is underpinned by legally owned wealth with title to named,
   known parties.  Every Buck participant -- issuers (who post collateral and
   create BuckCredits), holders, insurers -- has a persistent identity with
   real-world consequences.  Insurance costs, attestation quality, counterparty
   trust, and fee schedules all depend on your track record.

   This identity foundation extends naturally to oracles: your oracle track record
   is one facet of your overall Buck reputation.  A history of inaccurate oracle
   submissions doesn't just lose you oracle stakes -- it increases your insurance
   premiums, reduces the value of your attestations, and erodes counterparty trust
   across the entire ecosystem.

   The punishment for dishonesty is not mechanism-internal (stake confiscation); it
   is *ecosystem-wide reputation damage* that compounds across every financial
   relationship the participant has.

** The Oracle as Claim Ledger

   With identity, the oracle simplifies radically.  No Kalman filter.  No mode
   voting.  No staking within the oracle.  No challenge escalation.

   An oracle is a *public ledger of signed claims*:

   #+begin_example
   Claim {
       oracle_id:    bytes32        -- which oracle this claim belongs to
       reporter:     address        -- identified participant
       block:        uint64         -- Ethereum block number (slot key)
       value:        int256         -- claimed value at this block
       signature:    bytes          -- reporter's signature
   }
   #+end_example

   Anyone can create an oracle.  Anyone can post claims to any oracle.  Every
   claim is permanently recorded and attributed.  The oracle itself does no
   aggregation, filtering, or settlement.  It is a transparent record of who
   said what, when.

   Consumers choose which oracle (and which reporters within it) to trust,
   based on the reporters' track records.  The Buck system's BUCK_K controller
   uses whichever oracle the governance process has selected.

** Reputation is External and Cross-System

   In V1-V3, reporter reputation (R) was internal to the oracle -- an EMA of
   squared error, used to weight Kalman updates.  This reputation was session-
   local, address-specific, and had no consequences outside the oracle.

   In V4, reputation is a *property of the identity*, not the oracle:

   - Computed by comparing an identity's claims across all oracles against the
     values that were eventually accepted by governance or consensus
   - Permanent and public: your full history of claims is on-chain forever
   - Affects the entire Buck ecosystem: insurance premiums, attestation fees,
     counterparty credit limits, governance weight
   - Cannot be reset by creating a new address (identity is the anchor, not the
     address)

   This eliminates the need for internal oracle mechanisms to punish liars.
   The ecosystem does it automatically and far more severely than any per-round
   stake confiscation could.

** Why Internal Staking Becomes Unnecessary

   V1-V3 required reporters to stake tokens on each submission because there
   was no other way to make dishonesty costly.  With identity-bound reputation:

   - *Posting a claim is free* (or costs only gas).  No oracle-specific staking.
   - *The cost of lying is reputational*, not financial within the oracle.
     A single bad claim doesn't cost you $X -- it permanently marks your record.
   - *The cost compounds*: a pattern of inaccurate claims increases insurance
     costs, reduces attestation income, and can lead to governance de-selection.
     The NPV of this reputational damage far exceeds any per-round stake.
   - *Sybil attacks are impossible*: identities are tied to real-world legal
     entities and Buck holdings.  Creating 1000 fake identities requires 1000
     real entities with real collateral.

** Competitive Oracle Forking

   Persistent disagreement within an oracle is not necessarily adversarial.
   Edmonton gas prices and Calgary gas prices are both "correct" -- they're
   just measuring different things.  An oracle that forces them into the same
   number is wrong in both directions.

*** When Oracles Should Fork

    A fork is warranted when:

    - Reporters persistently cluster into groups posting materially different values
    - The disagreement is not due to one group lying, but due to genuine
      measurement differences (geography, methodology, data source)
    - Both groups have credible identities and track records

    The mechanism: any participant can create a new oracle at any time.  Reporters
    who disagree with the existing oracle's consensus simply start posting to a
    new one (or both).  There is no formal "fork" transaction -- the competing
    oracle already exists as an independent ledger.

*** What Makes This Different from Chaos

    Without governance, anyone creating oracles is just noise.  The Alberta Buck's
    governance provides the signal: *which oracle(s) does the BUCK_K controller
    actually use?*

    The answer is determined by the Buck community through stake-weighted voting.

** Oracle Governance: Stake-Weighted Identity Vote

   When an oracle is contested -- either because of suspected corruption, or
   because a fork has created competing oracles for the same asset -- the Buck
   community votes on which oracle(s) to use for BUCK_K computation.

*** Vote Weight

    Each identified participant's vote is weighted by their total Buck-system stake:

    #+begin_example
    vote_weight(identity) = (issued_buck_value + held_buck_value) * time_discount
    time_discount = 2^(-age / halflife)
    #+end_example

    Where ~age~ is how recently the participant was active (issued or transacted),
    and ~halflife~ is a governance parameter (e.g., 90 days).  This means:

    - Active participants have more say than dormant holders
    - Large issuers (who have the most at stake if the oracle is corrupted) have
      the most influence
    - Historical holders who have exited the system have negligible weight
    - No separate "governance token" -- your Buck stake IS your governance stake

*** Vote Mechanics

    #+begin_example
    1. Contest initiated: any participant can call contest(oracle_id)
       by posting a bond (prevents spam)
    2. Nomination period: participants nominate replacement oracle(s)
       (may include the incumbent)
    3. Voting period: stake-weighted identity vote
    4. Resolution: winning oracle(s) become the BUCK_K feed source
       Contest bond returned if the vote changes the oracle selection
    #+end_example

*** Multiple Oracle Aggregation

    The vote need not select a single oracle.  The BUCK_K controller could
    aggregate from multiple trusted oracles:

    - Median of N selected oracles (robust to one outlier)
    - Stake-weighted average across selected oracles
    - Fallback chain: primary oracle with secondary if primary goes stale

    For commodity basket computation, different assets might use different
    oracles entirely: a Gold oracle from one group, a Silver oracle from
    another, each selected by governance vote.

** Track Record as the Core Mechanism

   The critical insight: in a system with persistent identity, *the track record
   replaces the incentive mechanism*.

   In anonymous systems, you must design mechanisms that make honesty
   incentive-compatible for each individual interaction.  In identity-bound
   systems, the mechanism is simpler: your entire history is visible, and
   everyone individually decides whether to trust you based on it.

*** What the Track Record Contains

    For each identity across all oracles:

    #+begin_example
    - Total claims submitted
    - Claims that matched governance-selected oracle's final values (within epsilon)
    - Claims that diverged
    - Mean absolute error across all historical claims
    - Streak data: longest run of accurate claims, longest run of inaccurate ones
    - Timeliness: how early in the submission window claims typically arrive
    - Oracle participation: which oracles this identity contributes to
    #+end_example

*** How Track Record Feeds Back

    The track record is not just informational -- it directly affects economic
    outcomes across the Buck ecosystem:

    | Track record signal       | Economic consequence                                  |
    |---------------------------+-------------------------------------------------------|
    | High oracle accuracy      | Lower insurance premiums on BuckCredits                |
    | Persistent inaccuracy     | Higher premiums, fewer counterparties willing to deal  |
    | Early submission pattern  | Preferred attestation provider status                  |
    | Oracle governance wins    | Track record of picking winning oracles = trust signal |
    | Participation breadth     | Active across many assets = systemic importance        |
    | Oracle creation success   | Created oracles that won governance = credibility       |

** Comparison: V1-V3 (Anonymous) vs. V4 (Identity-Bound)

   | Aspect                    | V1-V3 (anonymous)                       | V4 (identity-bound)                          |
   |---------------------------+-----------------------------------------+----------------------------------------------|
   | Reporter identity         | Ethereum address (ephemeral)            | Legal identity with Buck holdings             |
   | Sybil resistance          | Staking, reputation warmup              | Identity binding (impossible to Sybil)        |
   | Dishonesty cost           | Lose staked tokens (per round)          | Permanent reputation damage (ecosystem-wide)  |
   | Oracle structure          | Single oracle, internal competition     | Many oracles, external competition            |
   | Aggregation               | Kalman / mode / weighted average        | None (oracle is a claim ledger)               |
   | Disagreement handling     | Majority wins, minority loses stake     | Fork into competing oracles                   |
   | Oracle selection          | One oracle per asset (monopoly)         | Governance votes on oracle set per asset       |
   | Challenge mechanism       | Internal: bond, escalation, re-opening  | External: contest oracle via governance vote  |
   | Reward for honesty        | Share of liars' stakes                  | Good reputation -> lower costs, higher income |
   | Punishment for dishonesty | Lose stake, inflate R                   | Permanent record -> higher costs, fewer deals |
   | Flash crash handling      | Smoothed away (Kalman) or preserved     | Preserved exactly (no aggregation)            |
   |                           | (mode)                                  |                                               |
   | Complexity                | High (filter, smoother, escrow, etc.)   | Low (claim ledger + governance vote)           |

** What Remains from V1-V3

   - *Block-indexed time slots*: claims target specific block ranges
   - *Circular buffer*: only recent slots stored on-chain; history in archive nodes
   - *Feed fees*: consumers pay to read oracle values, funding the oracle's operation
   - *Early submission bonus*: not enforced by mechanism, but visible in track record
     (consistently early reporters build trust faster)
   - *Non-ergodic dynamics*: still present, but in reputation rather than stake.
     A liar consortium can temporarily dominate an oracle, but the permanent record
     means they pay for it forever across the entire ecosystem.  The longer they
     lied, the worse their record, the higher the cost.

** What Disappears

   - Internal staking and stake redistribution
   - Kalman filter / mode estimation / any aggregation within the oracle
   - Challenge escalation within the oracle
   - Escrow and retroactive confiscation
   - Reporter R (measurement noise) weighting
   - RTS smoother and forward propagation

** Open Questions

   - *Identity bootstrapping*: a new participant has no track record.  How do they
     enter the oracle system?  Options: any identified Buck participant can post
     claims immediately (track record starts empty, trust is earned); or a
     minimum Buck holding is required to participate (barriers to entry, but
     prevents zero-stake spam).

   - *Cross-chain identity*: if the Buck expands to multiple chains, how does
     oracle reputation follow?  Portable verifiable credentials?  Cross-chain
     attestation bridges?

   - *Governance attack*: a wealthy attacker buys enough Bucks to dominate
     governance and selects a corrupt oracle.  Mitigations: time-discounting
     makes flash accumulation less effective; supermajority requirements for
     oracle changes; minimum participation duration before governance weight
     accrues.

   - *Oracle operator incentives*: if posting claims is free, what motivates
     someone to run an oracle and post accurate values?  Answer: the oracle
     operator is typically also a Buck issuer/holder whose assets depend on
     accurate BUCK_K computation.  Alternatively, feed fees provide direct
     revenue.

   - *Transition from Chainlink*: the current BUCK_K controller uses Chainlink
     price feeds.  The transition path: run identity-bound oracles in parallel,
     compare against Chainlink, build track records, then governance-vote to
     switch when the community trusts the new oracles.

* On-Chain / Off-Chain Architecture: References, Not Data

  The identity components (ZK proofs, homomorphic encryption, N/M recovery,
  attestation documents, title records) require expensive computation and large
  storage.  These are fundamentally unsuited to L1 Ethereum.  The right split:

  - *Off-chain*: computation, proof generation, data storage, oracle claim
    collection, reputation tracking, dispute evidence
  - *On-chain (L1)*: references, commitments, feature attestations that are
    trivial to verify (a signature check, a Merkle proof, a hash comparison)

  This applies to *everything* in the Alberta Buck, not just oracles.

** The Principle: On-Chain Stores References, Off-Chain Stores Data

   A recurring pattern across every Buck component:

   #+begin_example
   Off-chain:  Full data + expensive proofs
   On-chain:   commitment(data) + attestation_signatures
   Validation: cheap check that commitment matches, signatures are valid
   #+end_example

   The on-chain contract never sees the underlying data.  It sees a hash, a
   Merkle root, or a ZK proof verification result.  Anyone who needs the full
   data retrieves it from the off-chain layer and verifies it against the
   on-chain commitment.

** Component-by-Component Implications

*** Identity: ERC-3643 + Two Visibility Modes

    ERC-3643 (T-REX -- Token for Regulated EXchanges)[fn:1] has already solved
    most of the on-chain identity verification problem for regulated tokens.
    The Alberta Buck should adopt its architecture rather than reinvent it.

**** ERC-3643 Architecture (What Already Exists)

     ERC-3643 defines five interacting contracts:

     #+begin_example
     ONCHAINID[fn:2]      Per-identity smart contract (ERC-734/735 compatible).
                          Holds claims (hashed on-chain, data off-chain).
                          Deployed as upgradeable proxy via IdFactory + CREATE2
                          for deterministic same-address across EVM chains.

     IdentityRegistry[fn:3] Maps wallet addresses -> ONCHAINID contracts.
                          isVerified(address) checks:
                            1. Address is registered
                            2. ONCHAINID holds required claims
                            3. Claims are signed by trusted issuers

     ClaimTopicsRegistry  Defines what claims the token requires.
                          E.g., topic 1 = KYC, topic 7 = accredited investor,
                          topic 42 = licensed insurer (Alberta Buck-specific).

     TrustedIssuersRegistry  Defines who can issue those claims.
                          E.g., "CRA can issue topic 1 (KYC)",
                          "AIRS can issue topic 42 (insurer license)".

     Compliance           Additional transfer rules beyond identity.
                          canTransfer(from, to, amount) -> bool
                          E.g., per-country holder limits, maximum position size.
     #+end_example

     The token's ~transfer()~ function calls:

     #+begin_example
     require(identityRegistry.isVerified(_to), "Invalid identity");
     require(compliance.canTransfer(msg.sender, _to, _amount), "Compliance");
     #+end_example

     This is exactly the "one line added to BuckCredit.createCredit" pattern --
     but generalized to every token operation.

**** How Identity Gets Set: The Attestation Ceremony

     The process to activate an address for the Buck ecosystem:

     #+begin_example
     1. Off-chain: participant submits identity documents to a trusted
        issuer (e.g., a law firm, notary, CRA-approved KYC provider)

     2. Off-chain: trusted issuer verifies documents, generates a claim:
        - claim_topic = 1 (KYC verified)
        - claim_data  = hash(name, jurisdiction, ID doc hashes, ...)
        - claim_sig   = issuer.sign(claim_topic, claim_data)
        The claim data hash goes on-chain; the actual documents stay
        off-chain (on Holochain, IPFS, or the issuer's storage).

     3. On-chain: participant (or issuer on their behalf) calls:
        identity.addClaim(topic, scheme, issuer, sig, data_hash, uri)
        This stores the claim on the participant's ONCHAINID contract.

     4. On-chain: a registry agent (token issuer or governance multisig) calls:
        identityRegistry.registerIdentity(walletAddress, onchainId, country)
        This links the wallet address to the ONCHAINID.

     5. Now: identityRegistry.isVerified(walletAddress) returns true,
        and the participant can hold/transfer BUCKs, create BuckCredits,
        submit oracle claims, and vote in governance.
     #+end_example

     This is analogous to setting up an account to use a DeFi protocol with
     KYC requirements -- the ceremony happens once (or periodically for
     re-verification), and then on-chain operations just check ~isVerified~.

     For the Alberta Buck, the claim topics would include:

     | Topic | Meaning                    | Required for                    | Issuer              |
     |-------+----------------------------+---------------------------------+----------------------|
     |     1 | KYC verified               | All Buck operations              | Approved KYC provider|
     |     2 | Alberta jurisdiction       | Issuing Alberta-domiciled credits | Legal attestor       |
     |     7 | Accredited investor        | Large credit issuance            | Securities regulator |
     |    42 | Licensed insurer           | BuckCredit.createCredit          | AIRS or equivalent   |
     |    43 | Oracle reporter            | Oracle claim submission          | Self-attested + KYC  |
     |    44 | Governance participant     | Oracle selection votes           | Derived from holdings|

**** Two Visibility Modes: Private Transfers vs. Public Claims

     The Alberta Buck requires two fundamentally different identity visibility
     modes, depending on the operation:

***** Mode 1: Anonymous-but-Valid (BUCK Transfers)

      For ERC-20 BUCK transfers, the identity must be *verified* but not
      *disclosed*.  The transfer parties know each other, but the public
      blockchain sees only that two verified addresses transacted.

      #+begin_example
      What the blockchain sees:
        - address A transferred X BUCK to address B
        - identityRegistry.isVerified(A) == true
        - identityRegistry.isVerified(B) == true
        - compliance.canTransfer(A, B, X) == true

      What the blockchain does NOT see:
        - who A and B are (their names, jurisdictions, etc.)
        - why the transfer occurred (the underlying transaction)

      What the transfer participants see (off-chain):
        - encrypted receipt containing: sender identity, receiver identity,
          amount, purpose, timestamp, any additional terms
        - encrypted with the participants' public keys (only sender and
          receiver can decrypt)
        - optionally: a regulatory escrow key that allows authorized
          regulators to decrypt if needed (key escrow / threshold scheme)
      #+end_example

      The on-chain contract only calls ~isVerified~.  It never learns or
      stores who the participants are.  The full identity disclosure happens
      in the encrypted off-chain receipt.

      Implementation:

      #+begin_example
      // Buck.sol transfer override (ERC-3643 style)
      function transfer(address _to, uint256 _amount) public override returns (bool) {
          require(identityRegistry.isVerified(msg.sender), "Sender not verified");
          require(identityRegistry.isVerified(_to), "Receiver not verified");
          require(compliance.canTransfer(msg.sender, _to, _amount), "Compliance");
          _transfer(msg.sender, _to, _amount);
          compliance.transferred(msg.sender, _to, _amount);
          // Receipt creation happens off-chain (Holochain)
          // Only participants + optional regulator escrow can read it
          return true;
      }
      #+end_example

***** Mode 2: Public Identity (Oracle Claims, Governance)

      For oracle submissions and governance votes, identity is *intentionally
      public*.  "I, Perry Kundert, have submitted this Oracle reading, and
      stand by it for future credibility."  The whole point is that your name
      is on your claims so the track record builds public trust.

      #+begin_example
      What the blockchain sees:
        - address A submitted value V for asset G at block N
        - identityRegistry.isVerified(A) == true

      What anyone can look up (off-chain, public):
        - A's ONCHAINID has a public-identity claim:
          "Perry Kundert, Alberta, licensed insurer #12345"
        - A's full oracle track record: 847 claims, 99.2% accuracy,
          mean error 0.003%, earliest-quartile timeliness
        - A's governance participation: voted in 12 oracle selections,
          backed winning oracle 11 times

      Why this is public:
        - Your word is your bond.  The track record IS the reputation.
        - Anyone evaluating whether to trust oracle X can see exactly
          who is backing it and how reliable they have been.
        - Insurers who also report oracle values gain cross-domain
          credibility: "this insurer is accurate about prices" reduces
          the risk premium on their BuckCredits.
      #+end_example

      The ONCHAINID supports both modes through different claim types:

      #+begin_example
      // Private claim (topic 1: KYC) -- data hash only, off-chain encrypted
      identity.addClaim(
          topic  = 1,
          data   = keccak256(abi.encode(name, jurisdiction, docHashes)),
          uri    = "holochain://agent/kyc/encrypted"  // only issuer + subject
      );

      // Public claim (topic 43: oracle reporter) -- data in the clear
      identity.addClaim(
          topic  = 43,
          data   = keccak256(abi.encode("Perry Kundert", "Alberta", "insurer")),
          uri    = "holochain://agent/oracle-identity/public"  // world-readable
      );
      #+end_example

      The ~isVerified~ check works identically for both.  The difference is
      whether the ~uri~ points to encrypted or public off-chain data.

**** Off-Chain Identity Layer (Holochain)

     | Component               | What it stores                                     |
     |-------------------------+----------------------------------------------------|
     | Agent source chain      | All identity-related actions: claim requests,      |
     |                         | attestation receipts, oracle claim submissions,    |
     |                         | governance votes -- append-only, tamper-evident     |
     | KYC documents (private) | Encrypted with participant's key + issuer's key.   |
     |                         | Regulatory escrow key optional (N/M threshold).    |
     |                         | Referenced by ONCHAINID claim URI                  |
     | Public identity (opt-in)| Name, jurisdiction, licenses, credentials.         |
     |                         | World-readable via DHT.  Referenced by public      |
     |                         | claim URI on ONCHAINID                             |
     | Transfer receipts       | Encrypted per-transfer: sender + receiver keys     |
     |                         | + optional regulatory escrow key.  Contains full   |
     |                         | transaction details (identities, amounts, terms)   |
     | Oracle claims           | Full claim history (value, block, signature).      |
     |                         | Public for public-identity reporters.  Aggregated   |
     |                         | into Merkle root committed on-chain                |
     | Reputation scores       | Computed from oracle claim history vs. governance-  |
     |                         | selected oracle values.  Publicly queryable        |

     The Holochain DNA (application rules) enforces:

     - Agents can only write to their own source chain
     - Claims must have valid signatures from registered issuers
     - Transfer receipts must be encrypted (no plaintext identity leaks)
     - Oracle claims must be signed by the submitting agent's key
     - Reputation is computed deterministically from public claim data

**** On-Chain Contracts: What Changes

     | Contract            | Current                        | With ERC-3643 identity            |
     |---------------------+--------------------------------+-----------------------------------|
     | Buck (ERC-20)       | ~transfer~ with no checks      | Add ~isVerified~ + compliance     |
     |                     |                                | checks per ERC-3643               |
     | BuckCredit (ERC-721)| Any address can be insurer      | ~createCredit~ requires          |
     |                     |                                | topic 42 claim (licensed insurer) |
     | BuckKController     | Reads Chainlink                | Reads OracleCommitment           |
     |                     |                                | (unchanged from V4 proposal)      |
     | *New*: ONCHAINID    | N/A                            | Per-identity contract (ERC-3643)  |
     | *New*: IdRegistry   | N/A                            | Address -> ONCHAINID mapping      |
     | *New*: ClaimTopics  | N/A                            | Required claims for BUCK          |
     | *New*: TrustedIssuers| N/A                           | Authorized KYC/attestation providers|
     | *New*: Compliance   | N/A                            | Transfer rules (jurisdiction, etc)|
     | *New*: OracleCommit | N/A                            | Latest oracle values per asset    |

     The "new" contracts are standard ERC-3643 components[fn:4], not custom code.
     The only Alberta Buck-specific work is:

     1. Defining the claim topics (table above)
     2. Registering the trusted issuers (KYC providers, AIRS, etc.)
     3. Writing the Compliance contract rules (jurisdiction restrictions,
        position limits, etc.)
     4. Modifying ~Buck.transfer~ and ~BuckCredit.createCredit~ to call
        the identity registry
     5. Writing ~OracleCommitment~ (simple value store with signature checks)

**** Encrypted Receipts: The Privacy Bridge

     The Alberta Buck needs a paper trail (receipts, audit history) without
     making every transaction's participants publicly visible.  The pattern:

     #+begin_example
     Transfer: A -> B, 1000 BUCK

     On-chain (public):
       Transfer(A, B, 1000)           // addresses are pseudonymous

     Off-chain (encrypted, Holochain):
       Receipt {
         sender:     "Perry Kundert (ONCHAINID 0x123...)"
         receiver:   "Alberta Energy Corp (ONCHAINID 0x456...)"
         amount:     1000 BUCK
         purpose:    "Insurance premium payment for BuckCredit #42"
         timestamp:  2026-03-14T15:00:00Z
         terms:      "Quarterly premium, policy ref AEC-2026-Q1"
       }

     Encrypted with:
       - sender's public key    (sender can always read)
       - receiver's public key  (receiver can always read)
       - regulatory escrow key  (regulator can read with N/M threshold)

     Stored:
       - On sender's Holochain source chain (their copy)
       - On receiver's Holochain source chain (their copy)
       - Receipt hash committed on-chain (optional, for proving existence)
     #+end_example

     Neither the sender's nor receiver's real identity appears on-chain.
     The on-chain contract verified ~isVerified~ for both addresses, confirming
     they are identified participants, but the identity details exist only in
     the encrypted receipt.

     A regulator with the escrow key can decrypt any receipt and learn the
     participants' identities.  This satisfies AML/KYC requirements without
     making every transaction publicly deanonymizable.

*** BuckCredit (Insurance NFTs)

    Currently, ~createCredit()~ lets any ~msg.sender~ be the insurer with no
    identity check.  With the off-chain identity layer:

    | Layer     | What lives here                                                  |
    |-----------+------------------------------------------------------------------|
    | Off-chain | Title documents, appraisal reports, insurance policy terms,       |
    |           | collateral attestation with N/M party signatures, ZK proofs      |
    |           | of collateral adequacy                                           |
    | On-chain  | ~CreditParams~ struct (unchanged), plus:                         |
    |           | ~collateral_root: bytes32~ (Merkle root of off-chain documents)  |
    |           | ~require(features[msg.sender] & FEATURE_INSURER != 0)~           |

    The ~createCredit~ function gains one line: check that the caller has the
    insurer feature bit.  All the heavy identity/attestation work happened
    off-chain before that bit was set.

*** Oracle Price Feed

    This is where the impact is largest.  The V1-V4 oracle designs -- Kalman
    filtering, mode voting, claim ledgers, reputation tracking -- all become
    *off-chain protocol*, not on-chain contracts.

    | Layer     | What lives here                                                  |
    |-----------+------------------------------------------------------------------|
    | Off-chain | Full claim history (every reporter, every value, every block)     |
    |           | Reputation computation (track records across all oracles)         |
    |           | Dispute resolution (evidence submission, re-evaluation)           |
    |           | Governance voting (stake-weighted identity vote on oracle set)    |
    | On-chain  | ~oracle_value(asset_id) -> (int256 value, uint64 block)~         |
    |           | ~oracle_root(asset_id) -> bytes32~ (commitment to claim set)     |
    |           | ~oracle_attestors(asset_id) -> address[]~ (who signed this value) |

    The ~BuckKController.compute()~ currently calls Chainlink's
    ~AggregatorV3Interface.latestRoundData()~.  With off-chain oracles, it reads
    a similar interface backed by the governance-selected oracle's latest
    committed value:

    #+begin_example
    function latestValue(bytes32 assetId) external view
        returns (int256 value, uint64 updatedAtBlock);
    #+end_example

    One storage read.  The entire oracle claim collection, reputation tracking,
    and dispute resolution machinery runs off-chain.

*** N/M Recovery and Multi-Party Agreement

    | Layer     | What lives here                                                  |
    |-----------+------------------------------------------------------------------|
    | Off-chain | Encrypted key shards distributed to M parties, recovery ceremony |
    |           | (collecting N signatures), shard recombination                   |
    | On-chain  | ~recovery_config(address) -> (uint8 N, uint8 M, address[] parties)~ |
    |           | ~recover(address, bytes[] sigs)~ -- verifies N valid signatures, |
    |           | transfers ownership                                              |

    The recovery ceremony is entirely off-chain.  On-chain just validates
    that N of the M registered parties signed the recovery request.

*** Receipts and Transaction Records

    | Layer     | What lives here                                                  |
    |-----------+------------------------------------------------------------------|
    | Off-chain | Full receipt data (amounts, counterparties, timestamps, terms),   |
    |           | cryptographic receipts with N/M party co-signatures              |
    | On-chain  | ~receipt_root: bytes32~ per account (Merkle root of all receipts) |
    |           | Updated periodically (batch commitment)                          |

    Any party can prove a specific receipt exists by providing a Merkle proof
    against the on-chain root.  The full receipt database lives off-chain.

** The Off-Chain Layer: What Platform?

   The off-chain layer needs:

   1. *Agent-centric data ownership*: each identity owns and controls their own
      claims, attestations, and records
   2. *Cryptographic integrity*: data is signed by the owning identity, tamper-
      evident, and independently verifiable
   3. *Availability without centralization*: data must be retrievable without
      depending on a single server
   4. *Complex validation rules*: ZK proof verification, N/M signature checking,
      reputation computation
   5. *Selective disclosure*: prove properties of data without revealing the data
      itself (ZK proofs of identity features, collateral adequacy, etc.)

*** Holochain

    Natural fit for agent-centric data.  Each participant maintains their own
    source chain (append-only log of their actions).  Validation rules are
    defined per application (DNA).  DHT provides distributed availability.

    Strengths: no global consensus needed for storage, each agent owns their
    data, validation is local.  Weakness: less mature tooling, smaller ecosystem
    than Ethereum L2s.

*** L2 Rollups (Optimistic or ZK)

    Run the oracle/identity/reputation logic as an L2 that periodically commits
    state roots to L1.  Fraud proofs (optimistic) or validity proofs (ZK) ensure
    correctness.

    Strengths: inherits Ethereum security, mature tooling, can run full EVM
    contracts off-chain with L1 settlement.  Weakness: still has global state
    (not agent-centric), sequencer centralization concerns.

*** Hybrid: Holochain for Data, L2 for Disputes

    Use Holochain for the agent-centric claim/attestation layer (where most
    activity happens -- posting claims, building reputation, routine oracle
    operation).  Use an L2 (or even L1) only for disputes and governance votes
    that require economic finality.

    Most of the time, the system runs entirely on Holochain.  The on-chain
    contracts see periodic commitment updates ("oracle X says Gold is $2905 at
    block N, signed by reporters [A, B, C]").  Only when someone disputes does
    evidence move to a chain with economic finality.

** Impact on the Existing Contracts

*** BuckKController

    Minimal change.  Replace ~AggregatorV3Interface~ with an
    ~OracleCommitment~ interface:

    #+begin_example
    interface IOracleCommitment {
        function latestValue(bytes32 assetId) external view
            returns (int256 value, uint64 updatedAtBlock);
    }
    #+end_example

    The ~_getBasketCost()~ function reads from this instead of Chainlink.
    The implementation behind ~IOracleCommitment~ is a simple contract that
    stores the latest governance-approved value per asset, updated by
    authorized submitters (identified by the feature bitfield).

*** BuckCredit

    Add one require to ~createCredit~:

    #+begin_example
    require(identityFeatures[msg.sender] & FEATURE_INSURER != 0,
            "Caller not attested insurer");
    #+end_example

    Plus a ~collateralRoot~ field in ~CreditParams~ for the off-chain
    document commitment.

*** Buck

    No change.  It already just calls ~buckCredit.totalCurrentValue()~ and
    ~buckK.compute()~.  The identity and oracle layers are transparent to it.

*** New: IdentityRegistry Contract

    A small new contract that stores identity feature bits and attestations:

    #+begin_example
    contract IdentityRegistry {
        mapping(address => uint256) public features;    // bitfield
        mapping(address => bytes32) public identityRoot; // off-chain commitment

        function attest(address subject, uint256 featureBits, bytes32 root,
                        bytes calldata attestorSig) external;
        function revoke(address subject, uint256 featureBits) external;
    }
    #+end_example

    ~attest()~ verifies that the caller (or the signature) belongs to an
    authorized attestor, then sets the feature bits.  The actual identity
    verification happened entirely off-chain.

*** New: OracleCommitment Contract

    Stores the latest governance-approved value per asset:

    #+begin_example
    contract OracleCommitment {
        struct Commitment {
            int256  value;
            uint64  updatedAtBlock;
            bytes32 claimRoot;       // Merkle root of supporting claims
            address[] attestors;     // who signed this commitment
        }
        mapping(bytes32 => Commitment) public latest;  // assetId -> latest

        function commit(bytes32 assetId, int256 value, bytes32 claimRoot,
                        bytes[] calldata sigs) external;
    }
    #+end_example

    ~commit()~ verifies that the signers are governance-approved oracle
    reporters for this asset (checked via ~IdentityRegistry.features~),
    then stores the value.  ~BuckKController~ reads from ~latest~.

** What This Means for Storage and Gas

   | Component          | Current on-chain storage       | With off-chain layer          |
   |--------------------+--------------------------------+-------------------------------|
   | Identity           | None                           | ~2 words per address          |
   | Oracle claims      | N/A (uses Chainlink)           | 1 word per asset (latest val) |
   | Oracle history     | N/A                            | 1 word per asset (Merkle root)|
   | BuckCredit         | ~CreditParams~ struct          | +1 word (collateralRoot)      |
   | Receipts           | None                           | 1 word per account (root)     |
   | Recovery config    | None                           | N+2 words per account         |

   Total new on-chain storage is tiny.  The oracle goes from "store every claim
   from every reporter for every block in a circular buffer" (V2) to "store one
   int256 per asset."  The identity system goes from "nothing" to "2 words per
   participant."

** What This Means for the V1-V4 Oracle Code

   The Python simulation code (V1 Kalman, V2 time-series, V3 mode, V4 claim
   ledger) represents the *off-chain oracle protocol*.  It is not wasted work --
   it is the logic that runs on the off-chain layer (Holochain, L2, or a
   dedicated service) to collect claims, compute reputation, resolve disputes,
   and produce the commitment that gets posted to L1.

   The on-chain oracle contract is trivially simple: store the latest value,
   verify the submitters' signatures and identity features, expose a read
   interface for ~BuckKController~.

** The Full Stack

   #+begin_example
   Layer 1 (Ethereum L1):
     IdentityRegistry    -- feature bits, identity commitments
     OracleCommitment    -- latest value per asset, claim roots
     BuckCredit          -- ERC-721 insurance NFTs (+ collateral root)
     Buck                -- ERC-20 token (unchanged)
     BuckKController     -- PID controller reading OracleCommitment

   Off-chain (Holochain / L2 / hybrid):
     Identity service    -- KYC, ZK proofs, attestation ceremony
     Oracle protocol     -- claim collection, reputation, dispute resolution
     Document storage    -- titles, policies, receipts (content-addressed)
     Recovery service    -- N/M key shard management
     Governance service  -- stake-weighted voting on oracle selection

   Bridge:
     Periodic commitment updates: off-chain -> L1 (signed state roots)
     Dispute escalation: off-chain evidence -> L1 adjudication (rare)
     Identity attestation: off-chain proof -> L1 feature bit set (infrequent)
   #+end_example

   Most activity never touches L1.  Oracle claims are posted off-chain.
   Reputation is computed off-chain.  Identity is verified off-chain.  L1 sees
   only the results: a price, a feature bit, a Merkle root.
