#+TITLE: Regenerating the SNARK Artifacts
#+SUBTITLE: What breaks, in what order, and roughly how long it takes
#+author: Perry Kundert
#+date: 2026-08-18

This is the runbook for the day =build/snark/= is empty and the test suite is
red.  It was written immediately after doing exactly that, so the chain and
the traps below are observed rather than inferred.

* The one thing to understand first

Everything under =build/snark/= is a *MATCHED SET*.  A zkey, the Solidity
verifier exported from it, and every committed proof vector that verifies
against that verifier are produced by a single run and are only valid
together.  Groth16 setup is non-deterministic — the delta differs per run —
so regenerating any one member invalidates the rest.

The practical consequence, and the trap that cost a full session:

#+begin_quote
Regenerating ONE circuit's verifier silently invalidates every committed proof
vector that verifies through it.  The tests do not fail at regeneration time;
they fail the next time someone runs them.  *Run =make nix-test= immediately
after any =snark-*= target, before committing anything.*
#+end_quote

* Dev entropy: what these artifacts are and are not

=scripts/snark/setup.sh= contributes a FIXED entropy string,
=alberta-buck-dev-ptau-${POW}=, so the powers of tau are *reproducible* —
regenerating gives byte-identical ptau.  The zkeys are *not*: =groth16 setup=
draws fresh randomness for delta on every run.

So the honest status of everything in =build/snark/=:

- The toxic waste is *known*.  Anyone who reads =setup.sh= can forge proofs.
- This is fine for tests, CI and development, and is *not deployable*.
- Production requires a real multi-party ceremony.  Until that happens, every
  committed verifier in =src/= is a development artifact.

A public ceremony ptau (e.g. the Hermez =powersOfTau28_hez_final_*.ptau=
series) would be a strict improvement over the dev tau for the phase-1 half,
and is a drop-in: put it in =build/snark/ptau/= under the expected name and
=ensure_ptau= will reuse it rather than generating one.

* The ptau are the expensive part, and they are circuit-independent

| file | size | used by |
|------+------+---------|
| =pot12_final.ptau= | 4.5M | identity membership |
| =pot13_final.ptau= | 9.0M | identity membership (native) |
| =pot15_final.ptau= | 36M | mint, spend, =mint_batch_n1= |
| =pot16_final.ptau= | 72M | =mint_batch_n2= |
| =pot17_final.ptau= | 144M | =mint_batch_n4= |
| =pot18_final.ptau= | 288M | =mint_batch_n8= |
| =pot19_final.ptau= | 576M | =mint_batch_n16= |
| =pot20_final.ptau= | 1.1G | =mint_batch_n32= |
| =pot22_final.ptau= | *4.8G* | the A1 and A2 deposit folds |

=ptau_pow_for_n()= in =setup.sh= maps batch size to power: N=1 -> 2^15,
doubling per doubling of N, to N=32 -> 2^20.  Constraint count roughly
doubles with batch size, hence the ladder.

Two things worth internalising:

1. *Only =potN_final.ptau= matters.*  =ensure_ptau= checks for it and skips
   generation entirely if present; the =_0000= / =_0001= intermediates are
   scratch and need not be kept or restored.
2. *The ptau survive circuit changes.*  Editing a circuit forces a new zkey
   and verifier, never a new ptau.  Keep them.

=build/snark/= reaches *~30G* with the full pin set plus both folds.  Budget
the disk before starting; =pot22= alone is 4.8G and is generated late, so
running out mid-way wastes everything before it.

* DANGER: the only target that destroys ptau

=make snark-ptau= begins =rm -rf build/snark/ptau=.  It is the *only* target
that does.  It is now guarded — it prints what it will delete and requires
typing =delete-ptau= — but know what it is before you reach for it.

If you want fresh zkeys and verifiers against the ptau you already have, the
target is *=make snark-setup=*.

* The dependency chain, in the order it actually bites

Each step below closes one link and reveals at most the next.  Measured on an
M-series Mac with the ptau already present:

| # | target | needs | produces | time |
|---+--------+-------+----------+------|
| 1 | =snark-g1tie= | pot12/13 | G1-tie verifier + =test/vectors/g1tie/proof.json= (review evidence) | ~1 min |
| 2 | =snark-setup= | pot15..20 | =mint_batch_n*= verifiers (and legacy mint, spend) | minutes |
| 3 | =snark-fixtures= | 2 | =build/snark/mint_batch_n*/fixtures= | ~1 min |
| 4 | =snark-a2= | pot15..20 | =mint_batch_a2_n*= verifiers + fixtures | minutes |
| 5 | =snark-b1-membership= | pot20/22 | B1 membership verifier + its proof vector | ~5 min |
| 6 | =snark-deposit-fold-a1= | rapidsnark, pot22 | the A1 fold + its proof vector | *~20 min* |
| 7 | =snark-deposit-fold-a2= | rapidsnark, pot22 | the A2 fold + its proof vector | *~25 min* |
| 8 | =snark-e2e-fixtures= | ALL of the above | =alberta_buck/test/vectors/e2e/{a1,a2,b1}.json= | ~2 min |

Steps 6 and 7 are the long ones: they compile a C++ witness calculator for
about 3.3M and 3.8M constraints, need a 16 GB node heap, and generate =pot22=
(4.8G) if it is absent.  Do not run them under a timeout, and run them one at
a time.

Two switches save a lot of wasted setup:

- =WITNESS_ONLY=1= on either fold target stops after the witness stage: the
  circuit compiles, the honest witness satisfies it, and every attack witness
  is refused (the thief, the throwaway key and the A2 key split, the last one
  both by the witness builder and, with the builder's check stepped around, by
  the circuit itself).  Run it before spending a setup on a changed circuit.
- =DO_LEGACY=0= on =snark-setup= leaves the legacy =mint= and =spend=
  circuits alone.  They change rarely, and regenerating their keys would
  invalidate every committed proof that verifies through them for nothing.

Full pin set (=SNARK_PINS="1 2 4 8 16 32"=, both families) is substantially
longer — the =n32= circuits alone need =pot20= — and is only necessary if you
are changing the mint circuits.  For a red suite caused by a verifier
regeneration, =SNARK_PINS="1"= is sufficient: only N=1 feeds the e2e fixtures.

** Recipe: suite is red after regenerating something

#+begin_src bash
make nix-snark-g1tie                      # only if the g1tie evidence changed
DO_LEGACY=0 make nix-snark-setup          # the mint_batch pins
make nix-snark-fixtures
make nix-snark-a2                         # the A2 mint pins + their fixtures
make nix-snark-b1-membership
make nix-snark-deposit-fold-a1            # slow
make nix-snark-deposit-fold-a2            # slow
make nix-snark-e2e-fixtures
make nix-test
#+end_src

Commit the *whole* result in one commit: verifiers, proof vectors, and the
per-N =circuits/mint_batch_n*.circom= renderings that =SNARK_PINS= emits.
They are a matched set and splitting them across commits makes the tree
unbisectable.

* One convention: stock verifiers, EIP-197 packing

Every committed verifier is *byte-for-byte stock snarkjs output* (modulo the
contract rename), and every fixture generator packs =pi_b= in *EIP-197 order*
-- =[x_im, x_re]= per pair, the reverse of =proof.json='s -- which is the
same swap =snarkjs zkey export soliditycalldata= performs.  That is snarkjs's
own ABI: =verifyProof='s =_pB= parameter is specified pre-swapped, and the
caller does the conversion.

So there is exactly one rule when adding a prover or fixture path:

#+begin_quote
Read =proof.json=, and emit each =pi_b= pair as =[0][1], [0][0]= /
=[1][1], [1][0]=.  Never patch a verifier.
#+end_quote

The swap sites, should you need a model: =prove_mint.js= (JS),
=setup_g1tie.sh=, =setup_deposit_fold.sh=, =setup_b1_membership.sh= and
=test_verifier_regression.sh= (shell-embedded python), =gen_e2e_world.py=
(python).

** History, briefly

Until 2026-08 the repo ran TWO conventions: the JS provers swapped at pack
time against stock verifiers, while the Python/shell paths packed natural
order against verifiers post-processed by =fix_verifier_g2.py --b-only= (a
swap moved *into* the contract).  Both worked; they were not interchangeable;
and the patched half descended from a misdiagnosis of the snarkjs ABI as a
bug -- see =doc/historical/alberta-buck-verifier-bug.org=, whose CORRECTION
section has the verified archaeology.  The patcher also carried an involution
trap (applied twice, it undoes itself) that silently broke the regression
harness for a while.

Unified on the snarkjs convention; =fix_verifier_g2.py= is retired (it
survives in git history).  If a verifier ever rejects every proof again,
check the PACKING order first -- an unswapped =pi_b= yields an off-curve G2
point, the precompile fails, and =verifyProof= returns false for a proof
that verifies fine off-chain.

* Other prerequisites that are easy to miss

- *rapidsnark* — needed by both fold targets.  =make rapidsnark=
  unpacks =lib/rapidsnark-macOS-arm64-*.zip=.
- *circomlib* — =circuits/*.circom= include it from =node_modules=, so
  =npm install= must have run.  Note this makes the circuits derivative of
  GPL-3.0 circomlib.
- =test/RegressionTest.sol= imports from the gitignored =build/snark/regression/=,
  so a fresh clone cannot =forge build= until that circuit is generated.

* What "green" looks like

=make nix-test= -> *546 passed, 0 failed, 1 skipped (547 total)*.

If the failures mention "membership must verify" the g1tie verifier and its
dependents are out of step.  If they mention "bad mint proof" the mint
verifiers are.  Both mean the same thing: something was regenerated and its
vectors were not.
