* A' refined: the hiding registration presentation
:PROPERTIES:
:CUSTOM_ID: spec
:END:

This section is the design of record for the branch. It is a candidate for
cryptographic review; nothing here is proven beyond the sketches given.

** Keys

Issuer secret =(x, y)=. Issuer public key, stored by =trustIssuer=:

#+begin_example
X  = x*G2        (as today)
Y  = y*G2        (as today)
Y1 = y*G         (new, G1)
#+end_example

The registry checks =pairing(Y1, G2) == pairing(G, Y)= once, when the key is
trusted (two pairings, about 113,000 gas, once per issuer). A wrong =Y1= cannot
help a forger, because the verifier never uses =Y1=; it would only make every
honest registration fail, which the check prevents. =Y1= is stored so holders
have one canonical source for it.

Assumption change: publishing =y*G= in G1 puts the key in the committed-message
form of Pointcheval--Sanders (their Section 6), whose unforgeability rests on
the stronger assumption stated there, not on the plain scheme's. The issuer
must keep the signature base =h= with a discrete log unknown to holders, which
=ps_sign= already does by sampling it.

** Issuance, wallet storage, account derivation

Issuance is unchanged: the issuer canonicalizes the record, computes =m=, and
returns =sigma = (h, (x + m*y)*h)=. The raw credential never leaves the wallet;
it is not placed in receipts, calldata or the identity data channel.

For each new account the wallet samples fresh, independent, nonzero
=a, b, sk, r= and computes

#+begin_example
A   = a*sigma_1
B   = a*sigma_2 + b*Y1 = (x + m*y)*A + b*Y1
pk  = sk*G
E   = (R, C) = (r*G, m*G + r*pk)
#+end_example

=a= and =b= MUST be fresh per registration. Reusing =b= across two accounts
gives =P_1 - P_2 = m*(A_1 - A_2)=, a candidate test; reusing =a= repeats =A=.
Treat them exactly like ElGamal randomness.

** Registration proof

Witnesses =(m, b, r, sk)=, nonces =(m_t, b_t, r_t, sk_t)=:

#+begin_example
C1    = m_t*A + b_t*G          # one commitment for both credential exponents
T_C   = m_t*G + r_t*pk         # as today, same m_t joins the two relations
T_R   = r_t*G
T_key = sk_t*G
e     = H(A, B, R, C, pk, C1, T_C, T_R, T_key,
          registrant, chainid, registry, DOMAIN_v3) mod q
s_m   = m_t + e*m
s_b   = b_t + e*b
s_r   = r_t + e*r
s_sk  = sk_t + e*sk
#+end_example

Published: =issuer, pk, E, (A, B), (e, s_m, s_b, s_r, s_sk, C1, T_C, T_R, T_key)=.
Relative to today the pair is the same size, =C1= replaces =A_ps=, and =s_b= is
one extra scalar: 32 more calldata bytes. The domain string moves to
=.../Register/v3=. Decision taken in phase 1: the issuer address is *not*
added to the transcript. The registry already looks the key up by issuer
address, so the binding would add nothing the key lookup does not, and it
would thread a new parameter through the simulation cache, the registry
agent and every test.

** Verifier

#+begin_example
reject unless: registrant unregistered; issuer trusted; scalars canonical;
               A, B, pk, R not the point at infinity; all points on curve
(fs)  e == H(...)
(b)   s_m*G + s_r*pk == e*C + T_C
(c)   s_r*G          == e*R + T_R
(k)   s_sk*G         == T_key + e*pk
(a')  pairingCheck([ (s_m*A + s_b*G - C1, Y), (e*A, X), (-e*B, G2) ]) == 1
#+end_example

Credential-based contract binding reuses the identical proof with the target
contract as =registrant=.

** Why it is complete

=s_m*A + s_b*G - C1 = e*(m*A + b*G) =: e*P=, and
=pairing(B, G2) = pairing(A, X) * pairing(A, Y)^m * pairing(G, Y)^b
= pairing(A, X) * pairing(P, Y)=, so the product is
=[pairing(P, Y) * pairing(A, X) / pairing(B, G2)]^e = 1=.

** Why it hides (issuer-view unlinkability, sketch)

The only point derivable from the proof is =P = e^(-1)*(s_m*A + s_b*G - C1)
= m*A + b*G=. For uniform =a, b=, the triple =(A, B, P)= is distributed as
=(U1, x*U1 + y*U2, U2)= with =U1, U2= independent and uniform in G1, whatever
=m= is: =B= is a deterministic function of =(A, P)= through the issuer key.
Given =(A, B, P, pk, R, C)=, the rest of the transcript is simulatable in the
random-oracle model by choosing =e, s_m, s_b, s_r, s_sk= and setting
=C1 = s_m*A + s_b*G - e*P=, =T_C = s_m*G + s_r*pk - e*C=, =T_R = s_r*G - e*R=,
=T_key = s_sk*G - e*pk=. What the transcript reveals about =m= is therefore
what =(pk, R, C)= reveal, which is the existing ElGamal plaintext lock under
DDH in G1. The credential lock becomes information-theoretic and the plaintext
lock stays computational; issuer-blindness reduces to DDH, which is the
statement the main paper's theorem needs.

A party holding the issuer's secret learns nothing more: =B = x*A + y*P= holds
for every =(A, P)=. A party holding a candidate =m_i= can compute
=b_i*G = P - m_i*A= for every candidate, so the relation discriminates nothing.

** Why it is sound and non-reusable (sketch)

Two accepting transcripts with the same commitments and different challenges
extract =(m, b, r, sk)= with =pk = sk*G=, =E= well formed, and
=pairing(B - b*Y1, G2) = pairing(A, X + m*Y)=. So =(A, B - b*Y1)= is a plain PS
signature on the =m= encrypted in =E=: an accepting registration implies
knowledge of a credential on that identity, and forgery reduces to PS in the
committed-message key form.

A party that learns =m= from a receipt and sees a registration holds
=(A, B, P)=. Stripping =B= needs =b*Y1 = y*(b*G)= from =b*G= and =Y1=, a CDH
instance; rerandomizing =(A, B)= by =a'= leaves an unknown blinding =a'*b=; and
any accepting fresh proof implies knowledge of that blinding. Identity
disclosure therefore stops conferring registration authority under an honest
issuer. It does not stop the issuer itself from certifying the same identity
twice; that remains a policy problem.

** Degenerate inputs and public identities

The identity paper's "trivial signature" attack (choosing =t = 0= so the
published pair is =(O, O)=) becomes =a = 0=, =A = O= under A'. With =A = O= the
credential term vanishes and the verifier equation holds for every =m=, so the
=A != O= check is security critical, not hygiene. Reject =B = O= as well.

Public identity is unchanged: it is already a claim and a disclosure of the
record, not a property of the credential presentation. A holder who wants a
public account discloses =identity_data= and a verifiable decryption of =E_a=
to =m*G= under =pk_a= (the existing DLEQ in =verifiable_decrypt.py=). That
opens one account by choice and links nothing else, because no other account's
presentation can be tested against the disclosed =m=.

Revocation follows the same logic. Per-address revocation needs an address
the issuer has learned legitimately; under A' the issuer cannot find a
holder's addresses from chain data, so the unlinkable revocation route is the
epoch expiry the identity paper already describes.

** Drawbacks and open items, stated plainly

- Unreviewed. The hiding and soundness arguments above are sketches; the
  branch must not be merged to a production path without a written argument
  and independent review.
- Assumption change from plain PS to the committed-message key form.
- Fresh-randomness discipline for =a= and =b= becomes security critical.
- Does not address R5 (identity-derived A1/A2 receiving keys), R6 (issuance
  logs, policy metadata, accumulator admission), duplicate issuance by a
  malicious issuer, or the optional holder secret =u=.
- A wallet that ever exports the raw credential (backup formats, receipts,
  demos) reintroduces R3; the wallet and receipt schemas must forbid it.
- Not caused by A', but surfaced by the review: =identity_data= carries an
  =epoch= field, so =m= changes at renewal, while other passages treat
  =M = m*G= as invariant across a holder's accounts. Decide which is intended
  before the receipts and renewal sections are rewritten.

** =alberta-buck-paper.org=: what survives, what is re-proven

The review read all 1,811 lines. The paper contains no registration gas
figure, no ABI, no issuer-key notation and no public-identity trick, so the
revision is at the level of theorems and claims, not regenerated code. Two
findings drive it.

First, the issuer-blindness theorem's credential lock (535--538) is wrong as
shipped, independently of A': PS rerandomization hides which signature was
rerandomized only from a verifier who does not know =m=, and the issuer knows
every =m= it certified. The plaintext lock (538--545), the DDH
plaintext-checking reduction, is correct and survives verbatim. Under A' the
credential lock is replaced by the hiding lemma of the specification, and the
theorem's conclusion (a set of identities but no map to accounts; per-account
deanonymization only) survives verbatim with a computational qualifier.

Second, harvesting (R3) invalidates more of the paper than issuer-blindness
does. Every counterparty learns =m= by design (429--430), and today anyone
who knows =m= can register under that identity. That silently breaks the
read/write separation (426--436, 753--757), the non-frameability corollary,
the soundness clause of the receipt invariant as achieved, "impossible to
forge against the innocent" (112--113), "forgeable by no one" (1410), and
A1's "only Bob's identity can deposit it" (270--272): a prior counterparty of
Bob could register an account bound to =m_Bob=, deposit notes addressed to
Bob, or mint notes whose receipts name Bob as payer. A' supplies the missing
premise, that registration requires a secret which never appears on chain.

** Consolidated test plan

Negative tests, each with an honest control in the same test:

- R1: secret-key and public-key candidate scans over all registrations, zero
  matches.
- R2: proof-field scan with =C1= in the role of =A_ps=, zero matches; the
  candidate-adapted relation holds for every candidate (uninformative).
- R4: no plain signature recoverable from the transcript without =y=.
- R3: a party holding =m= and the transcript cannot produce an accepting
  registration; the legitimate holder can.
- Fresh-randomness discipline: two registrations with a reused =b= are
  linkable, so the wallet must never reuse it; test that the wallet's sampler
  never repeats and that the linkability exists when it does.
- Guards: =A = O=, =B = O=, off-curve points, non-canonical scalars, wrong
  chain, wrong registry, wrong issuer, replayed registrant, inconsistent =Y1=
  at =trustIssuer=.
- Cross-account: two showings of one credential share no point.
- Splicing: credential, ciphertext and key witnesses taken from different
  holders cannot be combined.

Positive tests: multiple accounts per identity register and verify;
counterparty confirmation decrypts exactly the certified identity; contract
binding with the credential form; four-backend parity; the A1, A2 and B1
Notes lifecycles.
