#+TITLE: BuckNet: responsibilities, transitions and invariants
#+DATE: 2026-10-30
#+OPTIONS: ^:nil toc:3

* Scope and status

This is a review and verification map for the *experimental clean-genesis*
=BuckNet= stack. It describes what the current code does and the properties
the system is intended to maintain. It is not a formal proof, a deployment
specification, or evidence from a five-year household economy. The existing
=src/Buck.sol=, deployed Notes contracts, and current economy use the legacy
model. The [[file:bucknet-economy-implementation.org][unified replacement plan]] owns the current sequence and
outstanding work; the [[file:net-demurrage-interface-migration.org][interface and proof reference]] details clients and Notes.

Several entries below are *requirements to prove*, not claims that all
rounding, market or adversarial cases are already proven. The selected
Carrying interface uses nominal ERC-20 amounts; its pool integration and
eventual service-contract allowlist still require the tests and controls
described below.

* Vocabulary and units

One external raw BUCK unit is =10^-6= BUCK. Let =Q= =10^36= fractional
units per raw unit, =Y= =365.25 days=, =T= =50Y= and =K= the current
18-decimal credit factor. The NFT's *coverage* and current insured value are
not BUCK supply. Outstanding *principal* is BUCK already issued, including
the amount initially left unspent and premium funding. A transfer or purchase
of BUCK does not by itself reduce that principal.

For NFT =i=, =P_i= is outstanding raw principal and =A_i= its capped
claimable BUCK-seconds. =D= is matured principal assumed by Jubilee. In a
correctly initialized, synchronized net system, the intended supply identity
after each successful transaction is:

#+begin_example
totalIssued = sum(P_i for open NFTs) + D = totalSupply
S = sum(A_i for open NFTs) + D*T, with 0 <= A_i <= P_i*T
#+end_example

The first equality is about principal, not the sum of account gross balances.
The second is the aggregate *claim benchmark*, not a promise of available
cash. A current aggregate requires all due maturity-heap entries to have been
processed. =JubileeClaimBook= exposes pending work and permits bounded public
processing; exact reads and updates fail while a backlog remains.

The target economic conservation identity is total *net* BUCK in the token's
accounts, including Jubilee cash and the BUCK actually held in pools, equal to
outstanding supply. Basket shares are claims on assets and must not be counted
again as BUCK. Arithmetic rounds at several points; the existing small-ledger
tests compare within one external raw unit. A global bound across arbitrary
accounts, long histories and checkpoint frequencies remains to be proved; do
not assert bit-exact conservation from those tests alone.

** Current balance and event semantics

An ordinary account has net held =H= and net issued-but-unspent =U=. Its
=balanceOf= is =floor((H+U)/Q)=; it may hold both while still owing multiple
NFT principals. Its unissued capacity is not included. The exact scaled parts
are exposed by =heldAndUnspentScaled=.

A Carrying account currently reports its *gross nominal transferable units*
from =balanceOf=, and =netBalanceOf= reports its full-value economic balance.
Sending nominal =n= moves its proportional net value, rounded down in scaled
units. A recipient can therefore receive less net value than =n=, although the
ERC-20 =Transfer= event reports =n=. =NetValueTransfer= separately records
the nominal amount and the actual full-value transfer component in =Q=-scaled
raw units; a zero net delivery can be valid. The fund's nominal gross includes gross
self-demurrage; it can exceed total issued supply even though its net value
cannot. Summing Carrying =balanceOf= values is not a supply calculation.

The intended use is a BUCK-neutral service such as an AMM, Notes pool or
insurer pool, not an ordinary long-term payment or savings account. Its
=balanceOf=, ERC-20 transfer amounts, allowances and events use nominal units;
apart from transfers and other explicit credits, those nominal units do not
decay. A Carrying recipient receives the same nominal units and their
proportionate carried fee. An ordinary recipient receives the associated net
amount. Users who leave funds in a service bear its pooled carried fee and
must be able to understand the resulting net value when they use it.

For example, a Carrying Notes pool with 100 nominal BUCK after ten idle years
has about 81.873075 net BUCK. A nominal 100 transfer delivers that net amount
to an ordinary recipient. The nominal event is not evidence of a full-value
payment. The Jubilee fund is a special Carrying recipient: its nominal balance
also increases through lazy demurrage credits, including its own gross fees,
even without an explicit ERC-20 transfer. These credits must be accounted for
separately when reconciling its balance and event history.

The desired future rule is to allow Carrying only for whitelisted contracts
providing BUCK-neutral services. This is not a current security property:
the registry authenticates deployed-contract binding and the binder can set
the initial Carrying flag or change it before freezing, subject to token mode
checks. There is no separate BUCK-service allowlist. Its authorization,
revocation and safe exit behavior remain implementation and audit work.
The owner has selected support for approved Carrying services owning and
using BuckCredit facilities. The current implementation still rejects that
case and rejects changing an indebted account to Carrying mode. Support must
be added deliberately; neither those checks nor this qualification should be
removed merely to make an API test pass.

** Why mint and burn use balance changes

The original =Buck= documentation and history define =mint(N)= in terms of
the spendable balance the caller wants at the current K, instead of requiring
the caller to predict how much coverage to activate. If =k= is K, =e= is the
insurance deposit per unit of present cover, and =V= is that cover, the
illustrative continuous calculation is ~N = (k-e)*V~. At ~k = 0.75~ and ~e = 0.10~,
requesting 100 spendable activates about 153.846154 of cover: about 115.384615
of credit capacity less about 15.384615 of premium. Actual raw-unit and face
rounding require the implementation's integer calculation. See the original
[[file:../../alberta-buck-ethereum.org::#mint-burn][mint/burn explanation]] for its selector and round-trip rationale.

In the old contract the activated, unused credit was included in =balanceOf=
even though it had not actually been issued as BUCK. The net token instead
issues actual BUCK immediately; its =balanceOf= excludes unissued capacity.
Both quantities need views, but their changes need not be equal. The new
compatibility contract is that a successful =mint(N)= increases actual
=balanceOf= by at least =N=, and =burn(N)= decreases it by at least =N=,
in net units for an ordinary owner and nominal units for an approved Carrying
owner. Use the measured external raw-unit difference after settlement, with
correct checkpoints and no arithmetic underflow; otherwise revert all state.
The maximum sentinel has its separately specified maximum-available meaning.

The old intent is not an unconditional guarantee of its implementation.
Temporary Foundry probes against the legacy contract reproduced three edge
cases: after a K reduction, an existing 50-BUCK shortfall absorbs half of a
=mint(100)=, leaving only a 50-BUCK visible increase; minting 1,000 for a
Carrying owner activates capacity without increasing its nominal =balanceOf=;
and a =burn(490)= after a year's accrued relief lowers visible balance by
about 488, rather than 490. These probes were exploratory and removed after
the run; permanent tests must exercise the new guarantees and regressions.

For intuition, take one ordinary facility and let =p= be actual principal
retired, =r= full-value Jubilee relief, and =f= the *net value* of the
original insurer's nominal refund. With no unrelated balance changes and
ignoring rounding, the owner's balance decrease is ~p-r-f~. For example,
~p = 100~, ~r = 6~ and 10 nominal refunded from an aged pool worth ~f = 9~ result
in an 85-BUCK decrease; a request for 85 may therefore retire 100 principal,
subject to all actual facility, K, fund-cash, mark and insurer constraints.
The inversion must use the actual selected facility and pool, not assume that
the nominal refund is worth its face in net BUCK. If no valid retirement can
achieve the requested decrease while preserving the refund and relief, it
reverts. The separately authorized 50-year lien release is unaffected.

For a Carrying owner, nominal balance and economic value must both be tracked.
A nominal refund increases its nominal balance while bringing the insurer
pool's proportional fee. Burning nominal units of the resulting pooled
balance removes only their proportional net value; that net value plus the
fund's net relief must equal principal retired. As an illustration of the
premium problem, an owner with 100 nominal worth 80 net should be able to
receive 20 newly issued nominal BUCK and pay a 10 *full-value* premium: the
owner ends with 120 nominal worth 100 net and the insurer receives 10 nominal
worth 10 net, while principal increases by 30. Transferring 10 nominal out of
the old mixed pool would not deliver 10 net. Direct allocation of fresh
premium to the insurer is a candidate, subject to identity, receipts, event,
reserve, self-pool, rounding and conservation checks; it is not implemented.

* State owners and transitions

** Initialization and trust boundaries

| Block | Preconditions | Postconditions / preserved invariants |
|-------+---------------+---------------------------------------|
| =BuckNet= constructor | Nonzero credit, K, registry and Jubilee addresses; deployment must link the exact maturity and transfer libraries. | One token owns its ledger, one new =JubileeClaimBook= and one new =BuckRenewalConsent=; the designated fund is immutable. The constructor alone does not establish verified identities or usable wiring. |
| Credit and registry wiring | The =BuckCredit= deployer calls one-shot =setBuck=; registry governance wires the same token; relevant identities and Carrying postures are registered. | Only that token can update facility issuance and coverage. Third parties cannot seize the credit's one-shot assignment. |
| =JubileeFund.configure= | Governance, unconfigured fund, token points to this verified Carrying fund, compatible basket/receipt and token are contracts. | The fund records one token and one basket and approves that basket. The one-time configuration must be verified against all actual deployed addresses and library code. |
| Fund identity binding | Before configuration, only fund governance may authorize or revoke an exact binding in a contract registry. The certified binder must separately complete the registry's checks. | The authorization pins the chosen binder, key and ciphertext to public Carrying posture. An unauthorized caller cannot set it; a revoked or differently flagged binding cannot be consumed. This is not the separate neutral-service allowlist. |

Governance selects the basket, keeper, reserve parameters and insurer binding;
these are trust assumptions, not consequences of the arithmetic. =BuckNet=
trusts its designated fund to calculate the marked policy; the token itself
checks the owner's authorization, bounds and liquid cap, not the mark's
fairness. Linked library =delegatecall= code runs in the token's context and
depends on the token's authorization and reentrancy guard. The linked
=BuckNetTokenOps= library carries both issuance and identity-checked
transfers: its issuance receives the host's own storage references and
immutable dependencies, keeps the original =msg.sender=, and is reached
under the host's guard. It must not be used as an independent ledger or be
called with a different host's state and assumptions.

** Account decay, issuance and transfers

| Block | Preconditions | Postconditions / preserved invariants |
|-------+---------------+---------------------------------------|
| Event-free account decay | Correct checkpoint and mode; outstanding supply is unchanged during the interval. | Both held and unspent net parts use continuous =exp(-0.02*t/Y)=, rounded down at =Q= precision. An untouched 100 BUCK is about 98.019867 after one year, not exactly 98. The independently accruing NFT target remains linear. |
| Fund checkpoint | Its prior net cash is no greater than issued supply. | With constant issued =P= and net cash =C=, ideal net cash becomes =P-(P-C)*exp(-t/T)=. Gross fees include the fund's own fees; self-payment is not a second net inflow. Lifetime flow counters retain whole units plus fractional remainders. |
| =issue(id,coverage,spendable,maxPremium,expectedPool)= | Owner is verified and ordinary; fund is verified Carrying; selected NFT is owned, authorized, not mature, and claim book is current. Its existing issuance age is checkpointed before adding fresh zero-age principal. Failures roll back all changes. |
| =transfer= / =transferFrom= | Verified parties and required identity fragments; allowance for =transferFrom=; sufficient sender balance in the mode's currently implemented units. | No NFT principal or total supply changes. A nominal Carrying transfer carries the proportional fee; an ordinary transfer debits full net value. The ERC-20 event states nominal units and =NetValueTransfer= states the exact scaled net movement. Integrator and privacy consequences remain to be evaluated. |
| Guarded V3 BUCK purchase | The pool is canonical for the configured factory and tokens, verified Carrying, and the ordinary verified recipient has any identity approval the token requires. The payer approves the guard's settlement token and specifies a net minimum or net exact output and maximum spend. | The pool pays BUCK directly to the recipient. The same transaction measures the recipient's scaled net increase, enforces the minimum, limits the authenticated pool callback, and refunds unused settlement; any failure rolls back the swap and payment. It does not change NFT principal. This one-pool guard is not a fair-price oracle or a multi-hop router. |
| Bounded V3 BUCK sale | The configured trusted Universal Router and Permit2 use a canonical, verified Carrying pool; the payer authorizes Permit2, specifies a positive settlement minimum and satisfies BUCK identity checks. Clients check pool mode before submission; that check is not atomic with the router transaction. | The router transfers BUCK directly from the payer to the pool and enforces the quoted minimum output in the swap transaction. The clients authenticate BUCK nominal/net transfer events and the settlement transfer from the saved receipt; a sale does not reduce a BuckCredit NFT. This assumes a standard settlement token and does not establish a fair price or support arbitrary fee-on-transfer tokens. |
| Registry mode change | The binder acts before the registry freezes the flag; only the registry callback changes the ledger. A facility with outstanding principal cannot become Carrying; the fund and registered insurer pools cannot stop being Carrying. A separate neutral-service allowlist is not yet enforced. | The ledger checkpoints the account before changing representation and preserves its net held/unspent value, subject to fixed-point rounding. The owner-NFT scan is currently unbounded in that owner's NFT count. |

Checkpoints must occur *before* changing the outstanding supply. =totalIssued=
is not the gross all-time BUCK-seconds integral. At present the exact capped
claim benchmark is separately maintained because an old NFT can stay open
after 50 years without its claim growing further. In the fund-cash equation,
=P-C= also includes BUCK held in the fund's own LP position: a fee on those
BUCK raises cash while reducing the position's BUCK value. It is not, by
itself, investment profit for the consolidated fund.

For a closed, no-return example, issue 100 BUCK and leave it untouched outside
the fund for 50 years. Ignoring rounding, the holder retains 36.787944 net and
the fund holds 63.212056 net. The full 100 BUCK experienced 100 BUCK of gross
fees over the period, but about 36.787944 of those fees were the fund paying
itself. The facility's baseline relief target is 100, not a guarantee of 100
liquid BUCK. Mature closure releases the lien and records the unburned
principal as a fund obligation; it does not invent the missing cash or burn
the holder's remaining balance. Future fees and actual investment returns can
help fund subsequent burns, subject to liquidity and the transaction cap.

** Facility age and bounded aggregate

| Block | Preconditions | Postconditions / preserved invariants |
|-------+---------------+---------------------------------------|
| NFT age view | NFT exists and its stored principal/checkpoint are valid. | =A_i=min(storedSeconds+P_i*elapsed,P_i*T)=. An issued but unspent BUCK starts aging at issuance. After average age 50 years its claim is capped even if the owner leaves the NFT open. |
| Additional issuance | NFT is not already mature; coverage, K and numeric bounds pass. | The prior capped age is checkpointed, then principal is added without adding age. This uses one pooled average age, not separate issuance tranches. |
| Partial reduction =p= | =0<p<=P_i= and the token synchronizes the book atomically. | The NFT removes =floor(A_i*p/P_i)= seconds, reduces principal by =p= and leaves the remainder's proportional age. The book's position and heap are updated in the same transaction. |
| Maturity processing | Caller gives a positive bounded step limit. | Each processed due NFT stops adding to the growing aggregate; exact aggregate reads resume only after the due backlog is cleared. Work and gas grow with the number of facilities, not all at once. Keeper incentives and adversarial backlog bounds are not yet established. |

Only the token can synchronize the claim book; the book reads the actual NFT
state rather than trusting arbitrary caller-supplied principal or age. Any
new token or migration must preserve that authorization and atomicity.

** Reduction and atomic renewal

Let =s=floor(A_i*p/P_i)=, =F= be scaled net Jubilee cash, and =L= the
receipt's net-of-gain-fee mark in raw full-value BUCK. With a current nonzero
benchmark =S=, the fund computes =r=min(p*Q, floor((F+L*Q)*s/S))=;
otherwise =r= is zero. This is marked proportional relief, not a guaranteed
2% return. The quote requires a usable price for contributing pools and the
specified spot/TWAP guard; a mark is not executable liquidity.

| Block | Preconditions | Postconditions / preserved invariants |
|-------+---------------+---------------------------------------|
| Authorization | NFT owner specifies exact principal, minimum scaled relief and deadline. | Only that request can be settled; it may be replaced or cancelled. A quote alone is neither authorization nor a payment guarantee. |
| Insurer preparation | After initial owner/consent validation, the original pool may be called to restore its nominal refund. | This is an external call under the fund lock, before the mark is read. Any market/claim change it causes must be reflected in the subsequent quote. Failure reverts the operation. |
| =reduce= | Exact current authorization, current benchmark, valid post-callback mark, =r<=F/10= and within the shared block budget, owner's minimum, pool refund/allowance, sufficient owner net BUCK and no worsened K shortfall. | Owner net and fund net jointly extinguish exactly =p= scaled value; total issued and selected NFT principal fall by =p=; its age and coverage fall proportionally and the original pool returns the proportional nominal deposit. No basket sale occurs in settlement. |
| =renew= | Same insurer and owner independently approve the exact terms, deadline, current NFT terms hash, principal and expected new insurer pool. The facility is not mature; the post-callback quote and all premium/K gates pass. For a nonzero new premium, the current default pool must equal the approved pool. | Actual relief is rounded down to whole raw units and retired; old premium is refunded from its recorded pool, new premium goes to the approved pool, coverage/terms and optional issuance change atomically. Remaining principal's claim age is reset to zero: any unpaid baseline target is not carried as a guaranteed claim. The old K shortfall may not increase. |

The token independently checks the operation-level =10%= limit, the shared
block budget and authorization. The first positive reduction, renewal relief
or deferred burn in a block snapshots =F/10=; later protected outflows share
the remainder, and incoming cash cannot increase it until the next block.
Zero relief does not start the budget. =availableReliefScaled= and the fund's
preview expose the smaller of the live operation cap and remaining budget;
they are quotes, not reservations. Failed transactions roll back budget use.
The owner minimum protects against a smaller payout, while reserve and market
checks protect only what they explicitly test. Any failed callback,
invalidated consent, insufficient funds, adverse mark or K violation must
revert the entire transaction, including callback effects and authorization.

The ERC-20 burn events must add to the integral principal retired; because
relief may be fractional, their individual owner/fund split is rounded. The
exact split is in =FacilityReduced=. Indexers cannot reconstruct each party's
exact net movement from those ERC-20 events alone.

** Maturity, refunds and the fund's investment

| Block | Preconditions | Postconditions / preserved invariants |
|-------+---------------+---------------------------------------|
| =closeMatured= | NFT owner calls after its pooled average issuance age reaches =T=; due claim entries are processed. | NFT and active coverage are removed; its full still-unburned principal becomes =D=. Total supply is unchanged and continues to accrue gross demurrage until later burned. Neither owner BUCK nor a basket sale is required. An unpaid original-pool premium remains independently retryable. |
| Deferred premium claim | Recorded original pool, beneficiary, nominal amount and required allowance/liquidity remain valid. | The original pool alone sends the nominal refund with its carried fee; no other insurer or Jubilee is charged. Failed automatic preparation/transfer leaves the claim, not the lien, outstanding. |
| =burnDeferred= | Authorized fund keeper/governance; positive principal <= =D= and <= 10% of current net fund cash and the remaining shared block budget. | Fund net, =D= and total supply fall by the same principal; the capped aggregate benchmark loses =principal*T=. No basket sale occurs in this burn. Tiny raw-unit dust can be unburnable under the strict cap. |
| Scheduled investment | Authorized keeper/governance, current aggregate, sufficiently matured budget and configured minimum; caller bounds nominal outlay, credited value and shares. | At most one fund-owned receipt exists; an existing receipt is increased in place. The spending is actual net BUCK, not the fund's nominal gross. Budget cannot exceed current observed excess. The half-life is of observed cash excess, not a direct ROI EMA. |
| Scheduled sale | Authorized keeper/governance; cash below target; requested receipt shares, routes and minimum actual net proceeds are bounded. | Only shares actually retired leave the receipt; newly received TOKEN is converted or the sale reverts. Existing in-kind inventory is not silently sold. Low-K exit and basket solvency guards remain in force. A sale can fail or have poor proceeds. |

** Planned compatibility and wheel transitions

The following are requirements for the [[file:bucknet-economy-implementation.org][unified replacement plan]], *not*
claims about the currently implemented prototype. The original =Buck.sol=
documentation is a source for the public contract and intended checks; retain
accurate explanations, but replace any signed-balance or implicit-repayment
description that no longer applies. The owner selected actual =balanceOf=
changes, approved Carrying facility owners, a shared block-wide cash budget
and the last published wheel mark, refreshed at burn preflight by a
valuation-only wheel call. The shared block budget is implemented. A
configured fund now refreshes a wheel-published mark during its existing
reduction/renewal path; a fund with no configured wheel still uses the earlier
guarded live mark. Compatibility =burn= and real deployment wiring are not
implemented.

| Proposed transition | Preconditions | Required postconditions and failure behavior |
|---------------------+---------------+----------------------------------------------|
| Compatible mint | The original caller owns every selected NFT and is verified; a Carrying caller is an approved neutral service; ordered/default selection, current K and marks, pool binding, premium, shared pre-mint reserve, account and supply bounds and claim-book state are valid. | The actual =balanceOf= increase is at least =N= in the caller's units, or the whole call reverts. Facilities, issuance, premium transfers, checkpoints and events agree atomically. Issued-but-unspent BUCK and NFT principal begin aging. Legacy parameters contain no caller-specified premium or pool bound; a separate bounded API must retain those protections. |
| Compatible burn | Owner and selected facilities are authenticated; requested =N= maps to exact principal, relief and coverage; the last valid published mark and insurer refund are usable and relief fits both the current-cash guard and shared block budget. | The actual =balanceOf= decrease is at least =N= in the caller's units, or the whole call reverts. Selected principal leaves supply, split between the owner's net value and the fund's full-value relief. NFT age, coverage, the original insurer's nominal refund and fund/claim counters move consistently. No amount is silently clipped and no basket sale occurs in the burn. |
| Wheel-derived fund mark | The burn requests the wheel's valuation-only refresh; for a fund with a position the resulting mark is usable, and freshness, position-consistency and price guards are satisfied. A fund with no position has a zero position mark. Liquid cash is observed at settlement. | The wheel may publish the mark and metadata, but its market and basket interactions are static: no swaps, keeper rewards, fund redemption or BUCK transfers under the token lock. Relief uses the resulting full-value BUCK mark without counting carried fees or underlying twice. A state-changing callback must occur before refresh or invalidate/revalidate it. Claim-derived mutual ownership needs a tested non-recursive policy. Invalid inputs fail closed; the mark is not cash or a promise of executable proceeds. |
| Wheel-driven fund investment | The wheel is authorized for the fund's bounded work; the reserve, matured budget, threshold, receipt ownership, net transfer and entry/minimum-share guards hold. | A new deposit creates one receipt or a top-up returns the same receipt ID, updating shares and basis from net value actually received. Fund outflow and budget counters use actual net BUCK, and failed work leaves no partial transfer or fake progress. |
| Wheel-driven fund redemption | The fund owns the selected receipt; its cash is below the selected target and share, route, exit, low-K and minimum-proceeds checks permit the work. | Only actually retired shares leave the position; the same receipt remains while shares remain. The fund records verified net BUCK actually received and any successfully converted new in-kind proceeds. Zero, partial, underwater and failed work are observable and do not mint cash, bypass exit guards or delete the remaining receipt. |
| Matured release | Owner requests closure after the selected facility's average issuance age reaches 50 years, and any due claim-book backlog is processed. | The lien and NFT close even if the fund or insurer is illiquid; unburned principal remains in total supply and the capped benchmark as a Jubilee obligation, and an unpaid nominal premium remains a claim on the original pool. Later fund burns observe the applicable liquidity guard. |

The wheel currently scans bounded slots with a cursor and an idle-per-block
memo; existing equity and response kinds catch failed basket work. Fund work
must re-arm the wheel when a cash, claim or mark change makes a slot due, and
must surface refusals and actual work in telemetry rather than treating a
caught failure as an executed replenishment. Integrating the fund's current
keeper entry points into that scheduler is future work. In particular,
=tick(maxWork,maxScan)= does not accept the route and slippage inputs the
fund's current scheduled investment and sale methods require; granting the
wheel keeper authorization alone cannot supply or validate those inputs.

The valuation-only entry is separate from that scan. Governance selects the
fund as a source, and publication reads its receipt through Solidity =view=
interfaces, hence EVM =STATICCALL= and static descendants. The wheel writes
only its mark and source/key/block/time metadata; the call does not advance
the work cursor or pay a reward. The fund requires that it remain the basket's
registered wheel and checks the configured source and a key derived from its
basket, receipt, shares and basis. Its quote checks the
current price band but may use a publication from an earlier block: its time
is visible on the wheel and a maximum quote age remains to be specified. A
reduction or renewal with a nonzero claim refreshes after any insurer
preparation, before quoting relief; failures roll back the publication. A
cash-only fund with no receipt has a zero mark. A test invokes the wheel
under the real BuckNet guard during issuance: token views work and a nested
token transfer is rejected. This is not yet a compatibility-burn test. The
current full valuation scans every constituent without a practical work/gas
limit; a supported size bound or coherent incremental approach is required
before making it mandatory in a production burn.

** Basket, identity and proofs

The experimental basket's =enableNetAccounting= mode holds actual BUCK and
does not issue its own credit. Entry/top-up must account for the *net change*
received, preserve receipt ownership, basis and shares, and avoid dilution.
An in-kind exit accounts for net BUCK actually received and returns residual
shares when applicable. Legacy leveraged mode is not evidence for a net-mode
leveraged basket: its own credit and Jubilee's receipt create a valuation
cycle analyzed in [[file:basket-jubilee-crossholding.org][the cross-holding note]].

Identity authorization is separate from monetary authorization. A valid
allowance does not replace verified parties or required bilateral receipt
fragments; public identities use the existing fallback rules. Mode hooks,
insurer binding, ERC-721 ownership and reentrancy checks must not be bypassed
by adapters. A new token address also changes the trusted registry wiring.

The existing =Notes= contract is immutable to its BUCK token and its mint and
spend amounts are note *face*. Its proof establishes the documented commitment,
membership, identity and nullifier relationships; it does not prove the
recipient's actual net BUCK balance delta. With the current Carrying ledger,
notes of different ages in one pool share the pool's average carried fee. The
new token event records the actual net transfer, but the existing Notes proof
and receipt do not bind or verify that event.
=NotesBuckNetAccountingTest= demonstrates both outcomes with stub proof
verifiers: it is an accounting test, not a cryptographic-security test.

The current spend proof's public inputs include chain, root, recipient,
nullifier, face and flavor but not a Notes contract or BUCK address. Each
Notes contract has its own nullifier mapping. The =NotesE2E_A1= replay test
uses real existing A1 proofs against two *independently funded* pools with the
same root and shows that each pool accepts the same spend. That experiment is
not a theft from one pool; it establishes that a migration must not duplicate
live claims between funded pools without a shared nullifier or an atomic,
otherwise non-replayable migration. See the interface migration plan for the
proof, key, ceremony and receipt consequences of each choice.
