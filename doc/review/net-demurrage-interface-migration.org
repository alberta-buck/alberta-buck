#+TITLE: Net demurrage: core, Notes and proof migration plan
#+DATE: 2026-10-30
#+OPTIONS: ^:nil toc:3

* Purpose and release boundary

This checklist extends [[file:net-demurrage-simulation-migration.org][the five-year and sandbox migration plan]] to the
shared Rust, Python and JavaScript interfaces, Notes and zero-knowledge proofs.
The experimental contracts and their [[file:net-demurrage-invariants.org][transition invariants]] are not yet a
production replacement. There is no supported state migration from legacy
=Buck= to =BuckNet=, nor from an existing Notes pool to another token. Do not
label legacy results, proof fixtures or a cash-only smoke test as validation of
the new system.

Python and browser-safe JS can link a built =BuckNet= artifact and locally
generated browser bundle for small EVM tests. Local package generation retains
the link references; no new package has been published and no production
deployment has been established. Experimental =BuckNet.issue= now requires an

check exact artifacts after every Solidity change rather than assuming a new

* Notes amounts and Carrying semantics

=Notes.buck= is immutable. A new BUCK token requires a newly deployed Notes
contract or an explicitly designed migration/adapter; changing a client ABI
cannot retarget an existing pool. Current mint pulls =totalFace= via
=transferFrom=, increments =noteFaceSum=, and publishes a proof-bound face.
Current spend consumes a nullifier, decrements the face sum and calls
=buck.transfer(recipient, face)=. All effects revert if the transfer fails.

In the current =BuckNet= prototype, a Carrying Notes pool's ERC-20 balance
and transfer amount are nominal. A 100-BUCK face can yield about 81.873075 net
BUCK after ten idle years; mixing a fresh note into an older pool shares the
pool's *average* carried fee, as intended for Carrying services. The
[[file:../../test/NotesBuckNetAccounting.t.sol][accounting integration tests]] demonstrate this with stub verifiers; they do
not prove a SNARK statement. The Python and Rust receipt
verifiers currently compare =txn.value= to =face=; the Python receipt model
also calls face the delivered value. Those claims must not be interpreted as
proof that a recipient obtained that many *net* BUCK.

For example, the controlled mixed-age test puts a fresh 100 nominal BUCK
beside 100 nominal BUCK worth about 81.873075 net. Each 100-nominal note can
then withdraw roughly 90.936537 net at that instant. Relative to separate
age attribution, that transfers about 9.063462 BUCK of value from the fresh
deposit to the old one. This follows the chosen pooled-fee policy; users need
to understand it, and the current proof system does not establish net value.

- [X] The user selected nominal =balanceOf=, standard transfer/allowance/event
  amounts and insurer refunds for Carrying pools. A Carrying-to-Carrying
  transfer preserves the nominal amount and carries its proportional fee;
  an ordinary recipient receives the associated full-value net amount.
- [ ] Implement the intended independent allowlist for BUCK-neutral service
  contracts. The existing binding checks contract control and identity but
  lets an authorized binder select Carrying; it is not that allowlist. Specify
  initial binding, adapters, flag changes, governance, provenance and proxy
  upgrades, and how delisting permits safe exits without confiscating balances
  or stranding insurer/Jubilee obligations. Test adversarial binding, mode
  changes, freeze, revocation, upgrades and migration; do not silently grant
  normal wallets or arbitrary contracts Carrying mode.
- [ ] Test real V3 mint, swap, collect and burn after an idle period in both
  token orders, with ordinary and Carrying participants. Nominal pool reserves
  can stay stable while their net economic value falls. In particular check
  swaps from a Carrying pool directly to an ordinary recipient: a nominal
  output or router minimum may differ from net received. The experimental
  =BuckNetSwapGuard= supports one canonical BUCK/settlement pool with an
  atomic net minimum or net exact output; real-V3 tests cover both token orders,
  refunds and refused limits. Complete LP mint/collect/burn, multi-hop,
  zero-value, adverse-token, callback and independent security review before
  claiming general integrator compatibility.
- [ ] Treat Notes face as nominal for the selected Carrying-pool design and
  disclose the pool-average carried fee and estimated net outcome. Test
  mixed-age entry and exit, dust, donations, extreme ages, insolvency and
  ordering. An individually aged or guaranteed net entitlement would be a
  different product with its own funding and proof requirements.
- [ ] Specify what a receipt claims: committed face, actual net delivered,
  or both. =BuckNet.NetValueTransfer= now exposes the transfer's exact
  =1e36=-scaled net raw units alongside nominal units. Define how a receipt
  authenticates the matching transaction/log, what its rounding means and how
  it survives reorganizations; assess the event's privacy and indexer
  implications. A nominal ERC-20 or Notes event alone is insufficient.
- [ ] Adapt =Notes= transfers and pool solvency checks to the selected API;
  protect approved amounts and identity-bound transfers, and test reverting
  transfer, a Carrying issuer, a Carrying recipient, mixed-age batches, all
  three flavors and real pool economics. Do not assume an ERC-20 return value
  implies the nominal face arrived as full-value BUCK.
- [ ] Update Python receipt builders/verifiers, Rust wallet core, PyO3 and WASM
  surfaces, JS wallet/sandbox and =notes_stack.py= together; version the
  schema and label historical receipts. Do not overwrite old receipt semantics
  or infer historical net delivery from a later balance.

** Candidate simplification: note shares rather than per-note clocks

If Notes promises a proportional claim on one continuously decaying BUCK-only
pool, a common net-value-per-share index can avoid a separate demurrage clock
for every note. Before a deposit, let =V= be the pool's net BUCK and =N= its
outstanding claim shares. A deposit of =x= *actual net* BUCK would receive
approximately =x*N/V= new shares; a spend of =s= shares would receive
approximately =s*V/N= net BUCK. A fresh pool needs an explicit initial index.
In the mixed-age example this leaves the old 100 shares worth about 81.873075
BUCK and gives the fresh depositor roughly 122.14 shares worth 100 BUCK, rather
than redistributing the old fee to the new depositor.

This is an optional design candidate for a future individually attributed
product, not a requirement of the selected pooled-fee service and not current
behavior or an approved change. A
note's committed =v= would denote shares rather than necessarily BUCK at
issue; the current mint proof/contract equates the sum of =v= with the BUCK
transfer and cannot simply be reused with a different interpretation. Specify
mint/spend rounding, fees, minimum output, direct donations, zero =V= or =N=,
insolvency, transaction ordering, concurrent proof races and what a receipt
can prove before selecting it. Compare privacy, cost and compatibility with
per-note age tracking and with an explicitly priced pooled-fee policy. If
Notes holds non-BUCK investments, =V= also needs a reliable valuation and
liquidation policy; the share index does not solve those problems.

* Proof statements and migration safety

Current =mint_batch.circom= / =mint_batch_a2.circom= constrain commitment
openings and the sum of faces; =spend.circom= constrains the note opening,
face, nullifier, recipient, chain, flavor and root; the folded A1/A2 deposit
gates and B1 membership/binding prove their separate identity relations.
These circuits do not currently establish a BUCK account's net balance or a
per-note demurrage history. Changing a monetary interpretation in Solidity
does not automatically change what an existing Groth16 proof establishes.

The current spend public inputs do *not* name the Notes instance or its BUCK
token. Nullifiers are stored separately by each Notes contract. The real-proof
[[file:../../test/NotesE2E.t.sol][cross-pool test]] mints the same A1 commitment using independently funded
deposits into two pools, then accepts the same spend/fold proof in each. That
does not steal from a single pool: each was separately funded. It does show
that copying a live root/claim into another funded pool while old claims remain
valid needs an explicit anti-replay mechanism; merely deploying a new token
and importing roots is not a safe migration. The diagnostic uses legacy
=Buck= and the existing fixture's test-injected allowance/identity fragments;
it is not a real-proof integration test of =BuckNet=.

- [ ] Choose and prove a migration protocol: for example, an atomic old-note
  spend/burn followed by a new note issuance, or a shared authenticated
  nullifier/claim registry with clearly defined freeze, snapshot and finality
  rules. Evaluate privacy, partial migration, chain reorganizations, failed
  retries, already-spent and unspent notes, duplicate roots and same-chain
  multi-pool replay. Independent funding does not make duplicated claims a
  valid migration of one old note.
- [ ] Decide whether a new proof version should bind the Notes instance, token
  and protocol/version domain. Trace every statement and transcript rather
  than assuming =chainId= alone binds the contract. New binding does not by
  itself migrate old notes or share old nullifiers.
- [ ] If a circuit/public input/relation changes, update Circom constraints,
  witness generators, prover input serialization, verifier adapters, contracts,
  Solidity field/range guards, Python and Rust/JS wallets and shared vectors
  together. Rebuild a matched circuit, proving key, verification key,
  on-chain verifier and proof fixtures. Keep old verification and claim paths
  as required by the chosen migration. If the relation does *not* change,
  demonstrate why existing proofs remain meaningful under the chosen amount
  semantics; do not regenerate keys merely because the token changed.
- [ ] Test soundness failures as well as happy paths: changed face or net
  amount, wrong token/pool/version/chain/root, stale root, reused nullifier,
  forged recipient/issuer, mismatched A1/A2/B1 identity binding, underfunded
  mint, failed transfer and rollback, field and token bounds, and concurrent
  old/new migration claims. Repeat with actual Groth16 and folded proofs, not
  only stubs. Retain the existing identity and privacy regression suites.
- [ ] Treat the checked-in development verifier/fixtures as development only:
  production proofs require a matched, audited setup with an appropriate
  trusted ceremony and artifact provenance. Do not overwrite or silently reuse
  existing proving keys during review or migration experiments.
